### [CRITICAL · CONFIRMED] PAUSE sends an ack-awaited M5 line after realtime '!' — the F13 spindle-sync deadlock; beam dwells energized on $32=0 and RESUME is dead on all machines

- **Location:** `src/components/panels/JobActionBar.tsx:186` · verified: Fable+Opus
- **What:** handlePauseResume's pause branch is: feedHold() (realtime '!') followed by `await machineConnection.send("M5")` — a line-protocol write that must acquire the job-long command mutex and then wait for GRBL's 'ok'. This is precisely the hazard class the emergencyStop docstring (connection.ts:408-423) says was eliminated ('M5 queues on the command lock forever'), but it survives on the pause path. Two mechanisms: (a) Under planner backpressure — the normal condition while streaming dense fill/engrave G-code; serial.rs:4-5's own invariants say a pump 'may legitimately hold [the lock] for MINUTES' — the in-flight job line's 'ok' is withheld until a planner slot frees. The '!' freezes the planner,
- **Fails when:** Machine with $32=0 (constant-power beam stays on in Hold — the very machines this M5 targets, per its own F16 comment). A fill job is streaming; the planner is full so the current line's pump holds the command mutex awaiting a backpressured 'ok'. User clicks PAUSE: '!' goes out realtime, head stops, beam keeps firing into one spot at cut power. The M5 blocks on inner.command.lock() behind the frozen pump and never reaches GRBL. ### [MEDIUM · CONFIRMED] saveToPath overwrites the project file in place with no atomic temp-and-rename — a failed or interrupted write destroys the last good copy

- **Location:** `src/lib/fileOps/index.ts:377` · verified: Opus
- **What:** saveToPath calls fsModule.writeTextFile(path, json) directly on the user's .kerf file. writeTextFile truncates then writes, so a crash, power loss, or disk-full mid-write leaves the only on-disk copy truncated/corrupt.
