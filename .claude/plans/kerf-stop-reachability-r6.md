**Summary.** Today a click on STOP while any dialog is open lands on that dialog's full-screen backdrop. On thirteen dialogs, the ? sheet, the palette and the canvas context menu that first click only closes the overlay. On the onboarding overlay and the recovery prompt it does nothing at all. No key reaches the stop, because every global shortcut is inert while a modal is mounted. When a stop is unconfirmed or fails, the only record is a console line, and the console is closed by default. And while the machine may be moving, the Help menu's Welcome Guide can reload the whole window, and the file menus can open native dialogs that may take the window. This plan makes STOP clickable above every overlay. It gives STOP two keys that work in every Kerf dialog and text box whenever the keystroke reaches Kerf; an input method or the system can take a key first, and the plan names where. The stop's outcome shows in the job bar the moment STOP is pressed, and it is replaced when the controller answers. "Stopped" shows only when Kerf can tie the answer to this stop and has sent nothing since. Kerf opens a native or blocking dialog only when it has fresh evidence the machine is idle with nothing in flight and knows its own last instruction to the laser was off (unknown counts as on), and while one is open it sends no job, line or motion byte. Nothing is added ahead of the reset byte.

**Key decisions.**
1. **STOP is raised in place, not portalled.** The STOP button and its outcome line get `position: relative` and `zIndex: STOP_LAYER_Z` (1,000,000, one exported constant). No dialog file is edited. A source scan plus a runtime walk make every other z-index stay below it, and they ban the browser top layer. This needs no A3.
2. **One operator stop function.** `operatorStop()` holds `handleStop`'s three statements, moved verbatim (`JobActionBar.tsx:110-112`). The button, both Stop keys and a new STOP on the crash screen all call it.
3. **Two Stop keys: Ctrl+. (⌘. on macOS) and Shift+Esc** (D1, **RULED by Lee 2026-10-05**, `.claude/DECISIONS.md:118`). Both are matched in one window capture-phase listener installed at module load in `main.tsx`, so they keep working after a React crash replaces the UI. The listener ignores auto-repeat. **Revision 3 drops the composition veto** (critic F3): a chord the page receives during IME composition is one the input method did not take, so it stops. A key the input method takes arrives as `key: "Process"` or not at all, and no matcher can recover it. The public claim is narrowed to match (Design C). It is a no-op exactly when the button is disabled (`!machineConnected`).
4. **The stop outcome is written after the stop is dispatched, never before.** Outcomes are grouped into episodes. An uncertain answer settles its episode at once; `confirmed` waits for every answer. **"Stopped" needs a clean episode** (revision 5, replacing revision 3's supersede and taint): from the first press to the last answer, Kerf reserved no other command, and at the press nothing was in flight except job and jog lines, which the native fence orders before the reset (DECISIONS 2026-09-24). Kerf does not get a native operation id, and it claims nothing about the order in which concurrent requests reach the wire. It needs no such claim, because a clean episode had no concurrent request that could write after the reset. The 7 s watchdog is a UI policy deadline, not a bound on native.
5. **Outcome writes are transactional, with an independent failsafe, and the dialog guard never trusts the store** (round-2 F4, round-4 F3). Each entry point computes its next state with no side effects, then commits it to a module variable, then publishes. Any fault ends in a visible message drawn straight into the page by `stopFailsafe.ts` and sets a module-level fault flag. The dialog guard reads that flag and the module's own outcome state directly, so a failed store write cannot open a dialog.
6. **STOP looks live in every state where motion is possible.** A7's solid rule is extended with `motionPending` and with any stop that is pending or uncertain.
7. **A blocking dialog needs nothing in flight, a fresh idle report, and output commanded off** (D2, **RULED by Lee 2026-10-05**, `.claude/DECISIONS.md:123`; round-2 to round-5 F1, round-5 F2). One module, `activityLedger.ts`, holds one set: every Kerf request that can write to the port or admit a job, from reservation until its IPC promise settles. A native dialog, `confirm` or reload may start only when that set is empty, the machine is disconnected or reports a fresh Idle taken after the last request settled, no stop is pending, uncertain or faulted, and Kerf's commanded output is off. Commands are classified the way the controller reads them: the existing normaliser (`normalizeGrblLine`, moved verbatim from `connection.ts:146-158` into `grblLine.ts`) strips comments and `/` as GRBL does, and the raw text is checked too, so the classifier is never less conservative than either. Output becomes *maybe on* when a possibly energizing line, byte or program is reserved, and **whenever the controller may have reset or run its stored startup blocks: every connect, every STOP and soft reset, `$H`, `$C`, `$RST=`, `$N…=` and `$SLP`** (round-5 F2; stock GRBL runs `$N` startup blocks after reset and after homing). It becomes *off* only through a **clean M5**: a line the controller reads as exactly `M5`, answered `ok`, reserved with the set empty and with nothing reserved before it settled (or a completed program ending that way). A banner, a confirmed reset, an Idle report or a disconnect never clears it. While a dialog is open, no job, line or motion byte is sent. Every blocking call goes through `src/lib/blockingDialog.ts`, whose Welcome Guide path releases its flag on every exit, including a reload that does not happen (round-5 F4). A refusal for output offers a plain "Laser off (M5)" button (D3, RULED 2026-10-05) that sends one `M5` through the normal send path; it clears the guard only by the same clean-M5 rule as any typed `M5`.
8. **No native change.** `serial_stop`, the fence, the submit lock and the single-reset contract are untouched. Every statement that runs before the dispatch today stays byte-identical, and so does their order.
9. **Five batches.** B1a (outcome core, activity ledger, failsafe) and B2 (the stop function, the keys, the crash screen) share no file and can run in parallel. B1b (wiring the ledger into the machine modules) waits on B1a. B3 (the raised STOP and the outcome line) waits on A1, A7, B1a, B1b and B2. B4 (the dialog seam) waits on A2, A10, B1b and B3. Documentation is a separate serialized commit after each merge (critic F7). Implementation complete and safety-qualified are recorded separately (critic F8).

### 2. Sidebar and job bar stacking

STOP paints at `z-index: auto` in the root stacking context. Nothing between it and the root creates a stacking context. The App root is `position: relative` with no z-index (`App.tsx:221-233`, :231). The main row is `display: flex; overflow: hidden` (:263). The sidebar is a flex column with `overflow: hidden` and no position (:284-292). The job bar's root sets only `flexShrink` and a border (`JobActionBar.tsx:173`). The STOP button has no position (:277-293). Its `disabled={!machineConnected}` (:279) is the only enable condition. Its cursor and opacity key off `jobRunning` (:286, :289), which A7 fixes. Two consequences follow. Any `position: fixed` element with z > 0 covers STOP. A z-index on STOP itself, with `position: relative`, competes in that same root context, so a single number can lift it over every overlay in the table, provided no ancestor gains a stacking context later. The sidebar and main row are flex containers, so a z-index on any flex item between STOP and the root creates a stacking context even without a position (the tripwire catches it).

The minimum window is 1000 × 600 (`src-tauri/tauri.conf.json:18-19`) and the sidebar is 300 px (`--panel-width`, `src/index.css:77`). A centred dialog reaches the sidebar when its width exceeds the window width minus 600 px. At 1280 the widest dialog (Dither, 640) ends at x 960, before the sidebar at 980. At 1000 every dialog over 400 px reaches it, and the ? sheet's `width: 90vw; maxWidth: 720px` (`ShortcutOverlay.tsx:148-149`) does too.

### 4. The stop path, end to end

1. **JobActionBar** `handleStop` (`JobActionBar.tsx:105-113`): `stopActiveSession()` (not awaited), `setJobRunning(false)`, `await machineConnection.emergencyStop()`. The comment at :106-109 calls the order safety-critical.
2. `stopActiveSession` (`jobSession.ts:243-262`) runs synchronously up to `await session.settled`: `cancel()` and a new `stoppingPromise`.
3. `setJobRunning(false)` notifies zustand subscribers synchronously. One of them is keep-awake's (`keepAwake.ts:47-65`), which on true→false calls `invoke("keep_awake_release")` (:59-63). **So on every STOP during a job the first IPC posted is `keep_awake_release`, and `serial_stop` is second.** `keep_awake_release` is an async command that does its work in `spawn_blocking` (`src-tauri/src/commands/power.rs:75-87`), so the stop is not queued behind it. The other subscriber is connection.ts's poll-suspend flag (`connection.ts:531-533`).
4. `emergencyStop` (`connection.ts:960-994`): `provisionalRevoke()` (store write, :962, body :86-88), `addConsoleLine("Emergency stop initiated")` (:963), then `invoke("serial_stop")` (:966-973). `@tauri-apps/api` 2.10.1's `invoke` is an async function whose body calls `window.__TAURI_INTERNALS__.invoke` synchronously (`node_modules/@tauri-apps/api/core.js:201-203`). The IPC is therefore posted before `emergencyStop` first yields, and before React re-renders anything. Because `invoke` is an async function it never throws synchronously; any failure arrives as a rejection. `serial_stop` takes no `conn` by design (the test helper `src/lib/machine/__tests__/setupConnInvoke.ts:9` lists the conn-carrying commands; motion trust exempts `0x18`).
5. Native `serial_stop` (`src-tauri/src/commands/serial.rs:1587-1592`) runs `serial_stop_inner` (`:1393-1582`) in `spawn_blocking`. The steps are: read `epoch_before` (`:1395`); single-flight `StopGuard` (`:1398`); close admission under `submit` (`:1432-1437`); invalidate the snapshot and set `job_abort`; clear `banner_observed`; write `0x18` on the realtime handle with one retry (`:1455-1482`), each successful write followed by `port.flush()` (`:1465`, `:1472`); wait up to 3 s for a banner (`:1504-1537`), each pass of which may block in `read_until` (`:1518`) before the deadline is checked again.
6. Outcomes (`StopResult`, `src-tauri/src/commands/serial_session.rs:129-146`, serde tag `outcome`): `confirmed {epochBefore, epochAfter, messages}` (banner seen; epoch incremented; phase Idle by CAS, `serial.rs:1539-1554`); `submittedUnconfirmed {epoch, messages}` (no banner in 3 s, or a concurrent disconnect moved the phase; phase Unknown, `:1555-1577`, the store at :1569); `submissionFailed {epoch, error, messages}` (both writes failed or no port; phase Unknown, `:1484-1497`, the store at :1493). Every message says beam state is unqualified.
7. TS (`connection.ts:978-993`): each message goes to the console, as an error on `submissionFailed` and a warning otherwise. On `submissionFailed`, `setMachineState("alarm")` (:983-985). On an IPC rejection, or a reply whose `messages` cannot be iterated, `setMachineState("alarm")` plus "E-stop send failed: … use the machine's physical stop." (:986-993). **Neither write checks the connection**, so a late failure from an earlier connection sets alarm on the current one.
8. Other callers of `emergencyStop`: `pauseJob` (`jobStream.ts:47-57`; Pause is stop), the stream's error and abort paths (`jobStream.ts:318`, :456), and `disconnect()` with a job or a run/hold state (`connection.ts:604-614`, awaited before teardown).

**Who can own a native stop (revision 3, critic F2).** `serial_stop_inner` has exactly four production callers, all in `serial.rs` before its first test module (`#[cfg(test)] mod tests` at :1686): `serial_stop` (:1590); `serial_stream_job_inner` after an event-sink failure (:1291); `serial_abort_job` (:1375); and `disconnect_inner_with_job` (:487), which is reached from `serial_disconnect` (:460) and from `serial_connect_inner` when a connection is already live (:335-337). No other `.rs` file calls it outside test files (grep of `src-tauri/src`, 2026-10-04: the other hits are `serial_trust_tests.rs`, a test module mounted under `#[cfg(test)]` at :5077-5079). So every native stop runs inside one of five commands TS invokes: `serial_stop`, `serial_stream_job`, `serial_abort_job`, `serial_disconnect` and `serial_connect`. TS invokes them at `connection.ts:966-973`, `jobStream.ts:228`, `connection.ts:878` (inside `abortJob`, which nothing calls), `connection.ts:638` and `connection.ts:483`. The native command runs strictly inside the interval between TS posting it and TS seeing its promise settle. That containment is what Design D uses in place of a native operation id.

**What a settled `invoke` means in the installed bridge** (revision 6, round-5 IPC finding; read 2026-10-05). `@tauri-apps/api` 2.10.1's `invoke` only forwards to `window.__TAURI_INTERNALS__.invoke` (`node_modules/@tauri-apps/api/core.js:201-203`). That function is injected by the `tauri` crate at the version `src-tauri/Cargo.lock:4581-4582` pins (2.10.2), from `scripts/core.js` and `scripts/ipc-protocol.js` in `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/tauri-2.10.2/` (the template is wired at `src/app.rs:1431`). Its promise settles only through two callbacks registered when the call is made (`scripts/core.js:81-110`), and `runCallback` fires one of them when the Rust response arrives, chosen by the response's `Tauri-Response` header (`scripts/ipc-protocol.js:42-57`). So a rejection comes either from the command's own `Err` after it returned, or from a synchronous throw while the message is built, before anything is sent (the executor at `scripts/core.js:83-110`). There is no timeout. Two further behaviours matter. If the IPC object is not ready yet, the call is queued and sent later (`scripts/core.js:71-79`, :99-108); the promise is pending throughout. And **if the custom-protocol `fetch` or the reading of its response fails, the same message is sent again over `postMessage`** (`scripts/ipc-protocol.js:59-68`). The failure handler runs after a response failed or the request never left, so any first execution has already finished or never started, and the promise settles on the second response: the TS lifetime still covers every native execution. But a command can then run twice, a `serial_stop` included. TB1 does not change this; it is named under Physical failure outcomes and parked, because two resets breach no safety property TB1 relies on, though they do breach the letter of the single-reset ruling. **Conclusion: in the installed versions, a settled promise means every native execution of that request has returned, or none ran.** Design D relies on exactly that and states it as a pinned fact with these citations. A Tauri upgrade re-opens it (a review item).

**The joiner can report an earlier stop.** A second `serial_stop` while one is in flight is a joiner. It polls for up to 3 s (`serial.rs:1403-1408`), then `take()`s `last_stop` (`:1409-1413`), or falls back to `submittedUnconfirmed` "joined existing stop operation". `last_stop` is written at the end of every stop (`:1494`, `:1579`) and never cleared at the start of one. It lives in the one `SerialSession` the app keeps for its whole run (`serial.rs:180`; `serial_session.rs:202`, :237). An owner whose banner wait runs the full 3 s outlasts a joiner that arrived within a few ms of it. That joiner then returns the previous stop's result as its own: possibly `confirmed`, possibly from an earlier connection, possibly from a native stop TS never saw the result of. TB1 handles this in TS (Design D) without touching native, and parks the native fix.

**A delayed reply can describe a stop that is already history** (revision 3, critic F2). Native sets phase Idle before the confirmed result is returned (`serial.rs:1539-1554`), and `serial_job_begin_inner` admits a job from Idle (`:1617-1631`, the check at :1618). So a stop can finish natively, its reply can still be in flight, and a new job or jog can be admitted in that gap. The reply then arrives describing a reset that happened before the new activity.

**The TS epoch watermark is not monotonic.** The native epoch is: it starts at 0 (`serial_session.rs:231`) and is incremented at connect (`serial.rs:405`), on a confirmed stop, and at disconnect (`:519`), and is never stored. But `resetStatusConsumer()` (`machineStatus.ts:283-287`) zeroes TS's accepted-snapshot watermark (`lastEpoch`, written at :191) at connect (`connection.ts:497`) and at disconnect (`:644`). So until the first status report is accepted on a connection, the snapshot half of any floor reads 0. Every real snapshot on a live connection has epoch 1 or more, so a watermark of 0 means "none accepted since the last reset".

### 6. Stored states and STOP today

`machineStateToStore` maps jog and home to `run` and GRBL's unknown to `alarm` (`machineStatus.ts:99`, :103, :107; unreachable fallback `alarm` at :109). Check and sleep map to idle. A new connection starts stale (`store/index.ts:674`). `motionPending` defaults false (:204). ### 9. What a blocking dialog must not overlap (revision 3, critic F1)

Revision 2's guard was `jobRunning || motionPending`. That admits three hazardous states. (a) **Running with pending false**: the jog send has returned, the snapshot says `run`, and neither flag is set (§6). (b) **Post-STOP uncertainty**: `operatorStop` clears `jobRunning` before the reset is even answered (`JobActionBar.tsx:110-112`), so the flag being false says nothing about the machine. (c) **A dialog opened while an admission is in flight**: an already-awaiting `serial_job_begin` (`jobSession.ts:58`) or motion `serial_send` (`connection.ts:681`) can be admitted natively after the dialog opens, because the JS thread keeps running under a native file dialog. An entrance check cannot prevent (c). It needs exclusion for the dialog's whole lifetime.

The status poll gives positive evidence only under two conditions. A `report`-kind answer is a fresh `?` read under the command lock (`serial.rs:120-130`). A `busy` answer returns the last snapshot (`:857-871`) and TS ignores it (`machineStatus.ts:165-167`). And the poll must be *dispatched* after the last command settled. The native command has returned before TS sees it settle, so such a poll's `?` was written after the command returned on the wire side, and a moving head reports `Jog` or `Run`.

| overlap with a large dialog at small windows | STOP sits over the dialog's bottom-right corner (§2) | identical: any surface above every dialog occupies that corner |

**Chosen: raised in place.** It is the smallest change that keeps one control, one handler and A7's presentation. Its one structural risk, an ancestor stacking context, is detectable both by a test and by a real hit-test, which the browser check runs at the base and head revisions named in Verification 5. The portal is not rejected categorically. It wins if the browser check finds a stacking context on STOP's ancestors that cannot be removed (for example a WebKit-specific compositing rule). Then B3 stops, and portal (ii) is the fallback, re-planned and re-critiqued. **A future surface that needs the top layer is a different problem** (revision 3, correcting revision 2, critic inversion): neither design survives the top layer, so such a surface needs its own top-layer-aware stop surface with input and focus proof, not a higher body z-index. The scan's top-layer ban stands until that plan exists. Under every design the focus contract is identical, as the row above shows: pointer access to STOP is never a focus-trap question, because the traps are keyboard-only, and keyboard access is the Stop keys.

**Raised whenever enabled, not only in motion states.** A conditional raise ("only while running, held, stale…") would make reachability depend on Kerf classifying the machine's state correctly. That classification is exactly what is uncertain here: Fire is not a motion command, a consoled move sits in the jog window, and a stale status reads idle. The z-index is unconditional. The cost is the corner overlap at windows narrower than about 1240 px. There STOP covers part of a large dialog's bottom-right corner, and a click meant for that corner can reset the controller (a lost job or lost homing, not a hazard). The browser check measures it at 1000 × 600, and the Parking Lot carries the follow-up.

### C. One stop function and the Stop keys

**`src/lib/machine/operatorStop.ts` (new, B2):**

```ts
/** The operator's STOP: the button, the Stop keys and the crash screen call this and nothing else.
 *  The three statements are JobActionBar.handleStop's, moved verbatim (order is safety-critical,
 *  DECISIONS 2026-09-20). Nothing may be added before emergencyStop(). */
export async function operatorStop(): Promise<void> {
  stopActiveSession(); // fire-and-forget: session settles after e-stop
  useStore.getState().setJobRunning(false);
  await machineConnection.emergencyStop();
}
```

`useStore.getState().setJobRunning` is the same function the component's selector returned (`JobActionBar.tsx:28`; zustand actions are stable). B3 replaces `handleStop`'s body with this call (`onClick={operatorStop}`). Until B3 merges, B2's equivalence test pins the keys' IPC sequence and store-write sequence to the button's.

**`src/lib/stopKey.ts` (new, B2):**
- `isStopChord(e)`: true for either chord, whatever `e.isComposing` says (revision 3):
  - **Chord 1, Ctrl+. (⌘. on macOS).** `(e.ctrlKey || e.metaKey)`, and either `e.key === "."` or (`e.code === "Period"` and `e.key === ">"`). Shift and Alt are not consulted. `e.key === "."` covers US and UK unshifted, AZERTY (where "." is Shift on the key whose code is "Comma") and Dvorak (where "." sits on the key whose code is "KeyE"). The `code` branch covers US and UK with Shift held, where the key reads ">". A bare `e.code === "Period"` is rejected: `code` names the physical US position, which is the letter V on Dvorak, so Ctrl+V (paste) would stop the machine; it is ":" on AZERTY.
  - **Chord 2, Shift+Esc.** `e.key === "Escape"` with `e.shiftKey` and none of Ctrl, Alt or Meta. Escape has the same `key` on every layout.
  - **Composition (revision 3, critic F3).** Revision 2 returned false whenever `e.isComposing`, for both chords, so both keys failed together while composing. That veto is removed. During composition an input method that uses a key reports it as `key: "Process"` (keyCode 229) or keeps it entirely (WebKitGTK skips events `handledByInputMethod`, `WebEditorClientGtk.cpp:91`, cited below). Neither matches a chord. So a chord that does arrive with `isComposing` true is one the input method did not take, and the operator meant it. The cost: the composition in progress may be lost, and an operator who presses a chord mid-composition stops the machine. That is an unwanted reset at worst, not a hazard. The guard was not removed casually: the jsdom cases pin both shapes, the browser run drives a real Chrome composition, and owner check D-7 qualifies delivery under IBus with a composing engine.
- `installStopKey()`: idempotent. It adds one `window` keydown listener with `{ capture: true }` and returns an uninstall function for tests. `main.tsx` calls it beside `installKeepAwake()` (`main.tsx:11`), before React renders, so it is the first `window` keydown capture listener the app registers.
- The handler, for a stop chord only: `preventDefault()` and `stopImmediatePropagation()`, then return if `e.repeat`, then return if `!useStore.getState().machineConnected` (the button's `disabled`, `JobActionBar.tsx:279`), then `void operatorStop()`. It writes nothing, posts nothing and moves no focus before `operatorStop`. Every other key passes through untouched, plain Escape included. - Why it cannot conflict inside Kerf: no binding uses "." (§3). A Ctrl/⌘ chord inserts no text in an input, textarea, select or contenteditable, and neither does Shift+Esc. Capture phase runs before the canvas text editor's `stopPropagation`, before every dialog's Escape handler, and before F7's modal guard, which this listener does not change (it is a separate listener, the way `?` and Ctrl+K are, `shortcuts.ts:71-72`). ### D. The stop outcome

**Where it is written.** Only in `emergencyStop`, so every stop shows: the button, the keys, the crash screen, Pause, the stream's own abort, and `disconnect()`. The target shape (B1b) changes nothing before the dispatch:

```ts
async emergencyStop(): Promise<void> {
  const store = useStore.getState();                                    // unchanged
  provisionalRevoke();                                                  // unchanged
  store.addConsoleLine("Emergency stop initiated", "warning");          // unchanged
  let attempt = 0;                                                      // bindings only, no work
  let sentOn: number | null = null;
  try {
    const reply = invoke<StopResultWire>("serial_stop");                // dispatch, unchanged position
    sentOn = connId;                                                    // TB1: first statement after dispatch
    stopReserve();                                                      // ledger: into the set; plain assignments, cannot throw
    attempt = beginStopAttempt(sentOn);                                 // total
    const result = await reply;
    for (const msg of result.messages) { /* unchanged console lines */ }
    settleStopAttempt(attempt, sentOn, connId, result);                 // total
    if (result.outcome === "submissionFailed" && sentOn === connId) store.setMachineState("alarm");
  } catch (e) {
    if (attempt) settleStopAttempt(attempt, sentOn, connId, { rejected: String(e) });   // total
    if (sentOn === null || sentOn === connId) store.setMachineState("alarm");
    store.addConsoleLine(`E-stop send failed: ${String(e)}. …`, "error");   // unchanged text
  } finally {
    if (sentOn !== null) stopRelease(attempt);                          // out of the set, exactly once
  }
}
```

No other JS runs between the `invoke(...)` call and `sentOn = connId`, so `sentOn` is the connection the dispatch was made on. The alarm guard is computed here, from `sentOn === connId`, and not from anything `stopOutcome.ts` returns. It guards both alarm writes, which is today's §4 step 7 defect. `sentOn === null` can only mean the dispatch line itself failed before assignment, which `invoke` being an async function rules out (§4 step 4); it then keeps today's unconditional alarm. With the connection unchanged (both 0 when disconnected, as in the existing tests) the alarm is written exactly as today. `serial_stop` is the one ledger command that does not go through `invokeMachine`, because the wrapper would add work before the dispatch; it joins and leaves the set through the two calls around it instead.

**`src/lib/machine/activityLedger.ts` (new, B1a; wired in B1b): one set, one wrapper, one clear rule** (revision 5). It replaces revision 4's two wrappers, the combined-wrapper flag, the listeners, the re-entry check and the on and off sequence numbers. It writes nothing to the store.
- **The set.** `inFlight`: every Kerf request that can write to the controller or admit a job, from the moment it is reserved until its IPC promise settles. The seven commands are `serial_send`, `serial_send_byte`, `serial_job_begin`, `serial_stream_job`, `serial_connect`, `serial_disconnect` and `serial_abort_job`, plus `serial_stop`. Status polls are not in it: they write only `?` (Diagnosis 10). Each entry is a small record (id, command, whether it is *fenced*, below), one per outstanding request.
- **One wrapper, `invokeMachine(cmd, args)`**, for the seven commands, driven by one table with two columns. *Admission*: refused while a blocking surface is open (every `serial_send`, every `serial_send_byte` except `0x18`, `0x85`, `0x21` and `?`, `serial_job_begin`, `serial_stream_job`). *Fenced*: a request whose write the native fence orders against a STOP (`serial_send` with `jobEpoch`, through `admit_and_write`, `serial.rs:613-616`; a `$J=` jog, which native classifies as a jog and writes through `admit_jog_and_write`, :549, :618-627; and `serial_job_begin`, which writes nothing and admits only in phase Idle, :1618). `serial_stream_job` is one row of that table (admission yes, fenced no); there is no other stream API (round-4 P2). The steps, one synchronous run in which no code outside the ledger executes:
  1. If the command is an admission and a blocking surface is open, return a rejected promise, `refused: blocking-dialog: A file dialog is open. Close it before starting a job or moving the machine.` Nothing is reserved. (`send()`, `beginJobSession` and `jobStream` already route a `refused:` rejection as a refusal: `connection.ts:715-720`, `jobSession.ts:59-62`, `jobStream.ts:287-293`.)
  2. Reserve: add the record to `inFlight`, note the current STOP count, raise the generation, apply the request's on effect and the clean-M5 candidate rule (below).
  3. If a STOP was reserved since step 2, remove the record and return a rejected promise, `refused: stopped: STOP was pressed while Kerf was sending this, so it was not sent.` Today nothing can run between steps 2 and 4, so this branch is a guard against a future edit, and a test-only hook (`_testBetweenReserveAndPost`, null in production, referenced only from `__tests__`, which the TS seam scan checks) exercises it (round-4 F2).
  4. Post `invoke(cmd, args)`. It is an async function and cannot throw synchronously (§4 step 4); a synchronous throw would still become a rejection.
  5. After the post, `queueMicrotask(activityPosted)`: the display-only notice that clears a settled "Stopped" line (Design D below). It runs after the request is posted and in the set, so a subscriber it triggers cannot open a dialog (the set is not empty) and cannot slip a STOP in front of the post (the post has happened).
  6. Settle, exactly once, when the promise settles: remove the record, apply the clear evidence if this request is the clear candidate, raise the generation.
- **STOP.** `stopReserve()` runs right after `invoke("serial_stop")` in `emergencyStop` and `stopRelease(attempt)` in its `finally`. It adds a `serial_stop` record, raises the STOP count, drops any clear candidate, and sets output *maybe on* (a reset can run startup blocks). STOP is never refused, delayed or reordered by the ledger.
- **Commanded output, and the clean M5** (revision 6 rewrite; round-4 F1, round-5 F1 and F2). `outputMayBeOn` is one boolean, `true` at start (unknown counts as on).
  - *One grammar, the controller's.* `src/lib/machine/grblLine.ts` (new, B1a) holds `normalizeGrblLine`, moved verbatim from `connection.ts:146-158`, which drops `( … )` comments, cuts at `;`, deletes every character at or below 0x20 and every `/`, and upper-cases, as GRBL's line reader does and as native's `normalize_grbl_line` does (`serial_session.rs:1008-1027`). `connection.ts` imports it from there (B1b), so the settings checks and the ledger share one contract. Two views of each line are checked: `norm` (normalised) and `raw` (upper-cased with whitespace removed, comments kept).
  - *On*, at reservation. A `serial_send` line is on if `norm` or `raw` contains `M`, then `3` or `4` with any leading zeros, and no further digit; or if `norm` does not start with `$` and contains an `S` whose value is not zero or does not parse; or if `norm` is a startup or reset trigger: it starts `$H`, `$C`, `$RST=`, `$SLP`, or `$N` followed by digits and `=`. Using both views means a disguised `M(x)3` or `M/3` is on (it is `M3` in `norm`), and `(M3)` is on too (it is `M3` in `raw`); the classifier is never less conservative than either view. A `serial_send_byte` is on unless it is `0x85`, `0x21` or `?`; `0x18` is on because it is a reset. A `serial_stream_job` is on if any of its lines is. Every `serial_connect` and every `serial_stop` is on (a reset).
  - *The one clearing kind:* a `serial_send` whose `norm` is exactly `M5` or `M05`, optionally after an `N` number, and which is not on by either view (so `M5 (M3)` never clears). A `serial_stream_job` also counts if its text's last spindle word (by `norm`) is `M5` and it contains no startup or reset trigger. Nothing else clears: not a banner, not a confirmed reset, not `S0`, `M2` or `M30`, not an Idle or any status report, not the `A:` field, not a disconnect.
  - *The clean-M5 rule.* The ledger holds at most one `clearCandidate`. At every reservation, of any command, STOP included: first, an existing candidate is dropped; then, if the new request is a clearing kind and the set was empty just before it was added, it becomes the candidate. When the candidate settles with its evidence, `outputMayBeOn` becomes `false`. Evidence: a result on the current connection that contains `ok` and no line starting `error:` or `ALARM` (for a stream, `complete` on the current connection).
  - *Why a clean M5 is sound after a reset.* A reset's startup blocks run before the controller reads its next line (protocol.c lines 52-63), and `$H` runs them before its own `ok` (system.c lines 194-198). A clean M5 is reserved with the set empty, so the reset or `$H` request had already settled, and the controller executes the M5 after any block those triggered. That is an ordering claim about one controller's single input stream, which GRBL processes line by line, not about Kerf's concurrent requests.
  - *Why it needs no wire-order claim about Kerf's own requests.* A candidate was reserved with the set empty, so every earlier Kerf request had settled. Any request reserved before the candidate settled drops it. So a counted clear was the only Kerf request alive for its whole life. This rests on one pinned fact: in the installed bridge, a settled promise means every native execution of that request has returned, or none ran (§4, "What a settled `invoke` means"; `scripts/core.js:81-110`, `scripts/ipc-protocol.js:42-68`). The Rust side matches: all eight commands are `async fn`s that await `tokio::task::spawn_blocking` (`serial.rs:418`, :454-465, :718-731, :744-754, :1349-1366, :1372-1380, :1587-1592, :1667-1672).
  - *How it behaves in normal use* (the cost Lee ruled on, restated for revision 6 in D2). After every connect, every STOP or Pause, every `$H`, and every soft reset, output is *maybe on* until a clean M5. A per-line job sends one line at a time, so its footer `M5` (`gcodeGen.ts:859`, `materialTestGcode.ts:183`) clears it at the end of a job that runs to completion. A successful Fire ends with a clean `M5` and clears it. Anything else leaves it on until the operator sends `M5` in the console with nothing else running, or a job or Fire runs to its end.

  **Commanded-output transitions (authoritative; the tests below derive from this table):**

  | event | `outputMayBeOn` |
  |---|---|
  | app start | on |
  | reserve: a line that is on by `norm` or `raw` (M3, M4, positive S, `M(x)3`, `M/3`, `(M3)`) | on |
  | reserve: `$H`, `$C`, `$RST=`, `$N…=`, `$SLP` | on |
  | reserve: `serial_connect`, `serial_stop`, byte `0x18`, byte `0x7E` or any byte but `0x85`, `0x21`, `?` | on |
  | reserve: a stream with any on line | on |
  | reserve: any other request | unchanged; drops any clear candidate |
  | settle: the clear candidate (an exact `M5` by `norm`, reserved with the set empty, nothing reserved since), `ok`, no `error:`, current connection | off |
  | settle: a clear candidate stream ending `M5` by `norm`, no trigger lines, `complete`, current connection | off |
  | settle: anything else, including a confirmed STOP, a `Grbl ` banner, an Idle report, a disconnect | unchanged |
- **Status evidence.** `activityGeneration()` rises at every reservation and settlement. `noteStatusReport(genAtDispatch, idle)` is called by `pollStatus`. `idleProven()` is true only when the last fresh `report` stored idle, was dispatched at the current generation, and the set is empty.
- **Blocking surfaces.** `tryBeginBlocking(isQuiescent)` checks, in one synchronous call that runs nothing outside the ledger except the predicate, that the set is empty and no surface is open, evaluates `isQuiescent()` inside a `try` (a throw means refuse), and only then sets the flag. `blockingEnd()` clears it. Because both this and `invokeMachine`'s steps 1 and 2 run no foreign code, one of them always sees the other: either the admission finds the surface open and is refused, or the surface finds the request in the set and is refused.
- **What is bounded, and what is not** (round-3 F7, kept). The ledger's own state is one record per outstanding request, one candidate, one boolean and two counters, and `stopOutcome` holds at most 32 attempt records and one timer. The set's size equals the number of outstanding Kerf requests, which TB1 does not cap and must not throttle: each STOP press is one pending promise and one native blocking task until it settles (`serial.rs:1587-1592`). A joiner returns within about 3 s (:1403-1413); an owner can block in `flush()` or `read_until` (:1465, :1472, :1518). Tokio's default blocking-thread cap is 512 ([tokio `Builder::max_blocking_threads`](https://docs.rs/tokio/latest/tokio/runtime/struct.Builder.html#method.max_blocking_threads)); whether Tauri changes it is not checked. B1b measures the TS side with 1000 never-resolving presses.

**`src/lib/machine/stopOutcome.ts` (new, B1a)**, a state machine whose view lives in the store as `stopOutcome: StopOutcomeView | null` (runtime only: `toProject()` does not read it, `fileOps/index.ts:507`, `autoSave.ts:40`):

```ts
type StopPhase = "pending" | "confirmed" | "uncertain";
interface StopOutcomeView { readonly episode: number; readonly connId: number; readonly phase: StopPhase; readonly overdue: boolean; readonly fault: boolean; }
```

- **Episode.** `beginStopAttempt(conn)` returns a new attempt id. The attempt joins the current episode if its view is `pending`, not overdue, and on the same `conn`. Otherwise a new episode starts: view `pending`, the floor and its "known" flag sampled, the overlap record taken (below), and the watchdog armed. A press after the watchdog has fired starts a new episode.
- **Settle early on uncertain; confirmed waits for all.** Any `uncertain` answer settles the episode as `uncertain` at once and clears its watchdog. That is final. A `confirmed` answer is only recorded. When every tracked attempt has answered `confirmed`, the view is decided by the rules below.
- **Classification of one answer.** `confirmed` only if `outcome === "confirmed"`, `epochAfter` is a finite number, the floor was known when the episode began, `epochAfter > floor`, and `sentOn === connNow === episode.connId !== 0`. A result whose `sentOn` differs from `connNow` changes neither the view nor `machineState`; its console lines still append and its `epochAfter` still raises the floor. Everything else is `uncertain`: `submittedUnconfirmed`, `submissionFailed`, an IPC rejection, an unknown outcome string, a malformed reply, a replay at or below the floor, and any `confirmed` in an episode whose floor was unknown.
- **The overlap rule: "Stopped" needs a clean episode** (revision 5, replacing revision 3's supersede and taint, round-4 F1 and F2). When an episode begins, `stopOutcome` records two numbers from the ledger, with no listener: the reservation count just after the first attempt's `stopReserve()`, and whether any *unfenced* request other than that attempt was in the set at that moment. The episode is **dirty** if any of these holds:
  1. an unfenced request was in flight at the first press (a console line, Fire, a setting, a realtime byte, a stream job, a connect, a disconnect, an abort, or another episode's stop). That is the critic's pending-before-press schedule: a held console `G1 M3 S100` makes the stop dirty, whatever order native runs them in;
  2. any request other than the episode's own later attempts was reserved between the first press and the last answer. That covers a job, jog or line started after the press, a re-entrant STOP's surrounding admission, and every stop-capable command, so it also covers the unseen native owners revision 3's taint handled;
  3. the episode began on connection 0, or one of its attempts was beyond the record cap.

  A fenced request already in flight at the press does not dirty the episode: the 2026-09-24 fence makes its one write either precede the reset in the shared output queue or be refused, and that is a native property with its own pinned tests, not an inference about request order. When every answer is a fresh `confirmed`, the view is `confirmed` only if the episode is clean and the connection is not faulted; otherwise it is `uncertain`. There is no third outcome and no cleared case. A confirmed view says the reset ran; it never sets the commanded output off (revision 6), because startup blocks can run after the reset.
- **The display notice.** `activityPosted()` (the ledger's microtask after each post) clears a *settled* `confirmed` view, so "Stopped" never stays above a newer command. It changes nothing else, and safety does not depend on it: the overlap rule is arithmetic on the ledger, not on this notice.
- **The floor stays a secondary rule.** `floor` is the max of every `confirmed` `epochAfter` received (dropped ones included) and the accepted-snapshot watermark (`machineStatus.ts:191`, through a new getter `acceptedSnapshotEpoch()`). If that watermark is 0 when the episode begins, the floor is unknown and every `confirmed` in it classifies `uncertain` (the first status interval after connect, §4). Snapshots and stop results share `session.epoch` (`grbl_status.rs:100-102`; `serial.rs:1395`; `serial_session.rs:275-277`).
- **The residual revision 2 stated is closed, not listed.** Revision 2 conceded that a native-internal stop after the last snapshot could leave an unseen `confirmed` that a joiner replays while a stalled native owner sits outside the TS episode. That owner now runs inside a command in the set, so the episode is dirty. What remains is a precondition, not a residual: a future native caller of `serial_stop_inner` outside the five commands would break the inference. `stopIdentityScan.test.ts` (B1b) fails the suite when the production caller set changes, and the B1 DECISIONS pin makes that change an amendment. The native fix (an operation id, or a joiner that accepts only a result written after it joined) stays parked; if it lands, the inference becomes a cross-check.
- **Native identity, compared** (round-3 inversion). A native operation id would replace the overlap rule's identity half, the floor and the Rust caller scan with one check. It needs edits to `serial_stop_inner` and its result type, a change to the golden `src-tauri/tests/golden/stop_result_fixture.json`, and its own plan and critic, inside the fence code the 2026-09-24 ruling protects. TB1 keeps the inference because it leaves that code untouched, and every rule in it only withholds "Stopped". When the parked native fix lands, its plan should retire the floor and the identity half of the overlap rule rather than add to them. An id alone would not order ordinary writes against a reset; that ordering is what the overlap rule and the clean M5 keep conservative.
- **Connection identity and lifetime.** `stopConnectionEnded(conn)` is called from `disconnect()` right after `connId = 0` (`connection.ts:636`), with the old id: a `pending` view on that connection becomes `uncertain` and its watchdog is cleared. `stopConnectionStarted(conn)` is called from `connect()` right after `connId = connected.connId` (`:488`): it clears any view from another connection, drops every attempt record, clears the fault flag and hides the failsafe. The ledger's set is not reset there, because it holds real IPCs that may still be running. `stopJobBegan()` is called from `beginJobSession` after a session is created (`jobSession.ts:65-66`; the only door for job, frame, material test and its frame, `JobActionBar.tsx:72`, :143, `MaterialTestDialog.tsx:240`, :263). It clears a settled view and never a pending one; native admitted that job only from phase Idle (`serial.rs:1618`), which no unconfirmed or failed stop leaves (`:1493`, `:1569`). A newer stop replaces the view. Loading a project or New does not touch it.
- **A STOP mid-disconnect.** Between `connId = 0` (`connection.ts:636`) and `setMachineConnected(false)` (`:639`), while `serial_disconnect` is awaited (`:638`), STOP is still enabled. A press there dispatches with `sentOn` 0. That episode is dirty from birth (connection 0, and an unfenced `serial_disconnect` in flight), so it can show `pending` and then `uncertain`, never "Stopped". The existing alarm-at-conn-0 behaviour is kept, as `connection.test.ts` pins.
- **Watchdog, replacement-safe.** `STOP_OVERDUE_MS = 7000`. **This is a UI policy deadline, not a bound on native** (revision 3, critic F6; revision 2's "exceeds native's own worst case … about 6.05 s" is withdrawn). Native's realtime write, its `port.flush()` (`serial.rs:1465`, :1472) and its banner loop's blocking `read_until` (:1518) are not bounded by anything this plan can cite, and the plan itself names a hung drain (Physical failure outcomes). So a native stop can outlast 7 s, and the watchdog then shows the uncertain wording, which is the safe direction. One timer per current episode, holding the episode id. When it fires it writes only if the view is still that episode and still `pending`, and then it sets `overdue: true`. Settling, clearing, a new episode and a connection end all clear it. A late answer for the same episode still settles an overdue view by the rules above. The view stays until replaced or cleared; nothing auto-hides it.
- **Bounded retention** (critic F4, X8). Attempt records exist only while outstanding, in one map capped at `MAX_TRACKED_ATTEMPTS = 32` across episodes on the connection. An episode keeps counts, not a list. A press beyond the cap is still dispatched (nothing ever refuses a stop) and gets an id, but it is untracked: its episode is dirty and its answer changes no view. Records are deleted on answer and all dropped at `stopConnectionStarted`. At most one watchdog timer exists at any time.

**Transactional writes and the failsafe** (revision 3, critic F4; revision 2's "a fault leaves the view exactly as it was" is withdrawn).
- **Ordering.** Every entry point (`beginStopAttempt`, `settleStopAttempt`, `activityPosted`, the watchdog callback, the three lifetime hooks) does three steps. *Compute*: `next = reduce(state, event)`, a pure function over an immutable copy. If it throws, nothing has changed. *Commit*: `state = next`, then reconcile the one timer (plain assignment and `clearTimeout`/`setTimeout`). *Publish*: `useStore.getState().setStopOutcome(viewOf(next))`. Zustand assigns the new state before it calls subscribers, so a throwing subscriber leaves the store updated but later subscribers, React's included, possibly un-notified. A stale "Stopped" can therefore stay on screen after a fault in any step.
- **Fault path, the same for every step and for the watchdog callback.** `stopFault(where, err)`: (1) `console.error` once; (2) set the connection's `faulted` flag, so every later view on this connection is at most `uncertain`; (3) `showStopFailsafe()` (below); (4) a best-effort `setStopOutcome({ …, phase: "uncertain", fault: true })` inside its own `try`/`catch`. `beginStopAttempt` returns 0 after a fault and `settleStopAttempt` returns nothing, so neither throws into `emergencyStop`, and the console lines, the alarm write and the rejection text are never skipped.
- **The authoritative state the guard reads** (revision 5, round-4 F3). `stopOutcome` keeps its current view and its fault flag in module variables, committed before any publish. `stopBlocksDialogs()` reads only those: it is true when the current connection is faulted, or the module's view is `pending` or `uncertain`. It touches no store and publishes nothing. Design G calls it inside `tryBeginBlocking`'s `try`, so if it ever throws, the dialog is refused. The store copy of the view is for the job bar only. So when both publications of a fault fail and the store keeps an old "Stopped", the guard still sees the fault and refuses, with the fault's own message (Copy ledger).
- **Which connection owns a fault** (revision 4, round-3 F4). A fault belongs to the connection of the event being processed: an answer's `sentOn`, a watchdog's episode connection, a lifetime hook's argument. If that is the current connection, or connection 0 (a press mid-disconnect, with no newer connection to protect), the fault path above runs in full. If it is an earlier connection (an answer whose `sentOn` is not `connNow`), the fault is logged once and nothing else happens: no flag on the current connection, no banner, no store write, and the floor is not raised. That is safe because a foreign answer changes no view (above), its processing publishes nothing, and its compute step is pure, so a throw there leaves the module state as it was. The earlier connection's view was already made uncertain by `stopConnectionEnded` and cleared by `stopConnectionStarted`. A fault inside `stopConnectionStarted` belongs to the new connection.
- **`src/lib/machine/stopFailsafe.ts` (new, B1a).** It owns `STOP_LAYER_Z` (B3 imports it from here). `showStopFailsafe()` creates or reuses one `<div id="kerf-stop-failsafe" role="alert">` appended to `document.body`, with inline styles only (fixed, top 0, full width, `pointer-events: none`, `z-index: STOP_LAYER_Z`, A1's danger colours with literal fallbacks), and sets its text with `textContent`. It touches no React node and reads no store. It is visible above every dialog, never takes a click, and never covers STOP, which is at the bottom of the sidebar. `hideStopFailsafe()` removes it, called only from `stopConnectionStarted`. If `document.body` is missing, it does nothing; nothing then reaches the screen, and that case is the crash-screen and e-stop path. It uses `role="alert"` because it exists only after a fault; `machineJobLoop.test.tsx`'s single-alert query never runs with a fault.

**Store rule.** JobActionBar reads `useStore((s) => s.stopOutcome)`, a whole-object reference that is replaced only on change (CLAUDE.md, React error 185), plus the scalar `motionPending`.

### G. A blocking dialog only with nothing in flight, proven idle and output commanded off, and nothing admitted while one is open (revisions 3 to 5)

**`src/lib/blockingDialog.ts` (new, B4) is the only door.** It is the one file in `src` (outside tests) allowed to name `@tauri-apps/plugin-dialog`, `plugin:dialog`, `confirm`, `alert`, `prompt` or a page-discarding `location` call. It exports:

The check and the flag are one synchronous ledger call, with nothing between them that could publish (Design D, "Blocking surfaces"). The lazy import keeps today's load behaviour.
- `reloadForWelcomeGuide(isDirty, reset)` (revision 6, round-5 F4: every exit defined). The flag is held from entry until the page is gone, or released on every path where the page survives:

  ```ts

  let navigating = false;
  try {
    if (isDirty && !window.confirm("You have unsaved changes. Reload to show the welcome guide?")) return; // Cancel
  ```

  The cases. Cancel on the dirty prompt: released at once, nothing reset, nothing reloaded. A throw from `confirm`, from the re-check or from `reset()`: released, a status message and console line, no reload. `reload()` returning and the page unloading: the flag is never released, which is right, because nothing may be admitted onto a page that is going away. `reload()` returning and the page surviving (navigation refused or failed): the timer releases the flag after 5 s and says so. **`machineQuiescent()`, the invariant** (revision 5: smaller, and reading no store field for anything the fault model lets fail). `tryBeginBlocking` has already required an empty set and no open surface; the predicate adds:


Each clause, and the hazard it closes:
- *The set is empty* (checked by `tryBeginBlocking`): no Kerf request that can write or admit, STOP, connect and disconnect included, is between reservation and settlement. This is the in-flight half of round-2 F1 (§9 c) and it covers Fire's three sends.

### Physical failure outcomes (software cannot certify beam extinction)

Kerf's best evidence is that the controller printed a reset banner after Kerf wrote `0x18`. That is what "confirmed" means, and no software state proves the beam is dark. Named failure outcomes, each with what Kerf shows:
- **The reset reaches the controller and the beam or motion does not stop.** DECISIONS 2026-09-05 records a `0x18` that failed to stop the beam on 2026-09-02 on the owner's vendor fork. Kerf may even show "confirmed". The confirmed line therefore tells the operator to check, and only the machine's e-stop is the stop.
- **The reset never reaches the wire.** A wedged USB adapter (`POLLOUT` reported, URBs not completing; Parking Lot, the stop's Step 5 `tcdrain`), a pulled cable, or a dead port. The result is `submissionFailed`, `submittedUnconfirmed` after 3 s, or a hang past 7 s (native's flush and read are unbounded here, Design D): the uncertain line.
- **The controller keeps executing what it already holds.** Up to the 127-block planner, and the 65,536-byte receive buffer in buffered mode (`[OPT:VHL,127,65536]`, DECISIONS 2026-09-05). The one admitted job line before the stop may run (ARCHITECTURE, Admission fence residuals). Console, Fire and settings writes are not phase-gated natively and can land after a stop (ARCHITECTURE residuals; Parking Lot; `serial.rs:628-631`). Kerf makes no claim about where such a write lands relative to the reset. One in flight at the press, or sent before the stop answers, makes the stop's episode dirty, so "Stopped" is not shown and the reset does not clear the commanded-output record.
- **The laser-switch wedge** (open, DECISIONS 2026-09-10 as amended 2026-09-27): the controller stops acking lines but answers `?`, and `0x18` is the recovery. A stop there may be unconfirmed if the banner read is lost (Parking Lot: the drain can discard a stop's banner).
- **The Stop key does not arrive.** An input method claims the chord (older IBus, Windows Chinese IMEs, a composing engine; Design C), the platform takes it, or a native select menu holds the keyboard. The other chord and the button may still work; D-2, D-3, D-7 and D-8 record what arrives. Otherwise only the machine's e-stop works.
- **The controller commands output by itself after a reset or Home** (revision 6). A stored `$N0`/`$N1` startup block runs after a reset unless the controller is in alarm, and after every successful `$H` (stock GRBL, [protocol.c](https://raw.githubusercontent.com/gnea/grbl/master/grbl/protocol.c) lines 52-63, [system.c](https://raw.githubusercontent.com/gnea/grbl/master/grbl/system.c) lines 194-198). So a confirmed STOP is followed, on such a controller, by whatever the block commands. The "Stopped" line still tells the operator to check the laser; Kerf's record stays *maybe on* after every reset and Home; D-10 records what the owner's controller holds.
- **A command can reach native twice** (revision 6). The installed bridge re-sends a message over `postMessage` when its custom-protocol request fails (`tauri-2.10.2/scripts/ipc-protocol.js:59-68`). A STOP can then send two resets, and a console line can run twice. TB1 changes neither and claims nothing about it; it is parked.
- **Kerf may have left the laser commanded on** (revision 4). A console M3 (disguised or not), a Fire whose M5 failed, a program stopped between its M3 and its M5, or any reset, connect or Home. Kerf tracks this as *maybe on* (Design D) and opens no blocking dialog and no reload until a clean M5 (an acknowledged M5 with nothing else in flight; revision 6 removes the confirmed stop and the banner reconnect as clears). Disconnect attempts the stop reset first; the attempt can fail and clears nothing. Even "off" is Kerf's commanded state: an acknowledged M5 is what the controller said, and DECISIONS 2026-09-05 records a reset that did not stop the beam. The check is still the operator's eyes and the machine's e-stop.
- **Kerf's window cannot take input.** After B4, no native dialog or `confirm` opens unless the machine was proven idle with nothing in flight and the laser commanded off, nothing is admitted while one is open, and the Welcome Guide cannot reload the window under the same conditions. What remains: the webview's main thread hung; a native select menu (D-8); a motion that starts on the controller by itself, which Kerf does not command. In those, STOP, the keys and the crash screen may be unreachable, and only the machine's e-stop works.
- **The display fails.** A fault in the outcome code shows the failsafe banner. If the page cannot render at all, the crash screen has its own STOP; if the webview is gone, only the e-stop works.
- **The app process exits.** Nothing is sent. Whether the port closing resets the controller is unknown for the vendor fork.
