- `Ctrl+.` is a known desktop collision on the owner's primary platform. GTK binds Ctrl+. (and Ctrl+;) to insert-emoji in text widgets, and IBus, the input-method daemon GNOME ships, has used `<Control>period` as its emoji-annotation hotkey; the widely reported symptom is that Ctrl+. in a text field in Chromium, Firefox or VS Code on a GNOME/IBus desktop opens the emoji picker and never reaches the page. That is exactly D-2 (focus in Preferences' width field, Linux WebKitGTK). The plan's R4 says "the button still works" and defers a second chord to "D1's answer can add" one later. For the only keyboard path of a safety control, the fallback belongs in B2, not in a later one-liner, and the collision belongs in Design C and in D1's option text so Lee decides with it in view. Fix: name the collision; ship two chords in B2 (Ctrl+. and a second that no IM or platform claims; the plan's own D1(b) Ctrl+Break is one candidate, or a chord with Alt that IBus ignores), and make D-2 an explicit "with IBus active" check that records which chord reached the page.

(stop)" passes in jsdom (synthesised `key: "."`) and fails on hardware. Fix: match `e.code === "Period" || e.key === "."` (code covers US-with-Shift and most layouts; key covers AZERTY, where "." is Shift on the `;` key), and synthesise the US case with `key: ">"`, `code: "Period"` in the test.

**6. Two problems.
- The settle-all rule delays the strongest guidance in the commonest stress behaviour. "The view leaves `pending` only when every attempt of the episode has answered" means that after a double press (owner plus joiner, the case the plan itself analyses), a joiner's `submittedUnconfirmed` at 3 s does not change the line; the operator reads "Stopping. …" until the owner answers or the 7 s watchdog fires. But the minimum rule already fixes the episode's final value the moment any attempt answers `uncertain`: nothing that arrives later can raise it. Waiting is therefore pure delay, up to about 4 s, in the one case the assertive wording exists for. Fix: an episode becomes `uncertain` on its first uncertain answer, at once; only `confirmed` waits for every attempt. Add the IPC test (A hung, B `submittedUnconfirmed` at 3 s → `uncertain` before 7 s) and a mutation (SR-14: uncertain waits for all answers) so the battery can fail it.

If it throws (a malformed reply reaching a code path the classifier did not expect), the `catch` call throws out of `emergencyStop`; `handleStop` and the key's `void operatorStop()` then surface an unhandled rejection, after the byte was sent but before the alarm write and the console line. ## Three stress tests

**Pre-mortem (three months out, it failed).**
1. *The key does nothing in a text box on Lee's desktop.* Ctrl+. was taken by the emoji picker; D-2 recorded it, a second chord was "to be added", and it was not. Lee, mid-job with Preferences open and the cursor in a field, hits Ctrl+. three times, then reaches for the mouse. Lost seconds, not a hazard, but the ? sheet advertised a key that did not work. We should have seen it in Design C before D-2.
2. *"Stopping…" for seven seconds.* A double press on a stop that goes unconfirmed. The joiner's uncertain answer at 3 s is held back by the settle-all rule; the operator waits on Kerf instead of pressing the e-stop because the line says Kerf is still sending. The assertive wording that exists for this moment arrived at 7 s.
3. *STOP under the backdrop again.* A later polish batch gave the sidebar `opacity: 0.98` for a fade; the tripwire test failed in that batch's run and the author edited the test's allow-list to merge. The DECISIONS pin is what should have stopped that; the review brief for every batch touching `App.tsx` needs to cite it.

Type-specific worst case: the beam stays on while the operator cannot reach a software stop. After TB1 that is the native-dialog and welcome-guide-reload class, where the controller runs the planner's 127 blocks (and, buffered, up to 64 KB of lines) with no UI at all; the plan names it and the e-stop is the stop. That is honest, and it is also why the guard should carry a date.

**Load-bearing assumptions.**
1. No ancestor of STOP creates a stacking context, now or after A2. Verified today; A2's spec adds only `overflowX: hidden`. High confidence; the tripwire guards it if its list is complete (dimension 3).
2. Ctrl+. reaches the DOM on the owner's desktop with focus in an editable field. Unverified and doubtful on GNOME with IBus. Medium-low confidence; consequence is a dead keyboard path. Resolve by shipping the second chord in B2 and recording D-2 with IBus active.
3. Native `epoch` is monotonic for the process and incremented at connect and disconnect. Verified (`serial.rs:405`, `:519`, no store). High confidence. The TS watermark is not monotonic (`resetStatusConsumer`), which is the dimension-8 point.
4. `invoke` posts the IPC before the first yield. Verified for `@tauri-apps/api` 2.10.1. High confidence; a future upgrade of that package should re-run B1's "not before dispatch" test, which it will, since it is in the suite.
5. The native joiner's semantics (poll ≤ 3 s, then `take()` `last_stop`). Verified. The plan's TS handling depends on it and the native fix is parked with an exact line.

**Inversion.** The portal wins if an ancestor stacking context cannot be removed, if a surface must use the top layer, or if STOP must be inside the open dialog's accessibility tree. The first two are false today. The third is partly true today: `aria-modal="true"` on every dialog hides the raised STOP from assistive technology while a dialog is open, and the plan parks it; the key is the AT path. That is an acceptable answer for now, and the Parking Lot line says so. Escape-as-stop would win only if dialogs did not close on Escape; they do (eighteen handlers). Raising STOP only in motion states would win only if Kerf's state classification were trustworthy during Fire, the jog window and stale status; the plan shows it is not. The rejections stand.

## Overall verdict

PASS, with seven CONCERN dimensions and no FAIL. The diagnosis is accurate to the line, the design keeps the stop path byte-identical ahead of the dispatch, the raise-versus-portal question is answered with a stated fallback, and the verification has a base run that must fail, trusted input, and a mutation battery that can fail each rule. The concerns are real and all fixable inside revision 2 without changing the design: the Stop key needs its desktop collision named and a second chord shipped in B2 with `e.code` matching; the episode should go `uncertain` on its first uncertain answer rather than waiting for the slowest; the floor should be presented as secondary to the minimum and closed for the no-snapshot interval; the welcome-guide reload is a found hole that needs a date, not a parking space; and three test specifications need tightening so they cannot pass tautologically. Nothing here makes the operator worse off than today, which is why this is a PASS with must-fixes rather than a FAIL.
