## Question 2: the JSX native-input scan and the ESLint rule

**Verdict: PASS.**

- **Coverage of the named forms.** The rule set closes the space by construction, not by enumeration: any JSX route to a real `<input>` must either write a literal `type` (caught: literal, `{"literal"}`, template) or pass a non-literal (caught: "any non-literal expression as an `<input>`'s `type`", "any spread attribute on an `<input>`"), and any non-JSX route must create the element (`createElement("input")`, caught), inject HTML (`innerHTML` family, caught) or mutate an existing element (`setAttribute("type", …)`, `x.type = "<literal>"`, `showPicker`, caught). A wrapper component that forwards a `type` prop fails at its own `<input type={props.type}>`, which is the case that matters. Every selector is expressible in `no-restricted-syntax`: `JSXAttribute[name.name="type"] > Literal[value=/^(file|color|date|time|datetime|datetime-local|month|week)$/i]` (esquery regex attributes take flags), `JSXExpressionContainer > Literal`, `JSXExpressionContainer > TemplateLiteral`, `JSXOpeningElement[name.name="input"] > JSXAttribute[name.name="type"] > JSXExpressionContainer > :not(Literal)`, `JSXOpeningElement[name.name="input"] > JSXSpreadAttribute`, and the member/call forms. The config already parses `.tsx` with typescript-eslint (`eslint.config.js:22`), and `*.config.js` is ignored, so the rule file cannot flag itself.
- **"No false positives today" is true at HEAD**: see Q1's enumeration; none of the banned forms exists in `src` outside tests. "Exactly the two sites" for the base run is what the tree shows.
- **Positive controls** are real: fixture files for each form (so a dropped selector fails its fixture, SR-148, SR-149), plus the base run at B5's parent that must report exactly `:313` and `:402`, which proves the instruments see real code before the sites change. The base run is a one-time artefact, as the plan's other base runs are ("The base for (e) to (g) is B4's parent"); consistent.
- **Limits stated honestly**: outside `src`, third-party components rendering their own inputs, and `<select>` (D-8). Three small edges are not named; none exists in the tree, so they are hardening rather than holes in the proof at HEAD.

Findings under Q2:

- **F2 (P3) — three unnamed edges, each closable at zero cost today.** (i) The DOM-assignment rule bans `x.type = "<literal>"` only; `el.type = someVar` and `el["type"] = …` pass both nets. The tree has no assignment to a `.type` member at all (grep `\.type\s*=[^=]` and `["type"]`: none), so ban every assignment to a member named `type`, computed or not, whatever the right-hand side. (ii) `document.write` and `Range.createContextualFragment` are HTML-injection forms not in the `innerHTML` list; add them. (iii) The scan's regex as written (Design G :402) is case-sensitive while the lint is case-insensitive; HTML types are case-insensitive, so add the `i` flag, and let the `createElement` selector match `document.createElement`, an imported `createElement`, and `"INPUT"`. These keep the two nets equally strict.
