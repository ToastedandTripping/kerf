**Summary.** Today a click on STOP while any dialog is open lands on that dialog's full-screen backdrop. On thirteen dialogs, the ? sheet, the palette and the canvas context menu that first click only closes the overlay. On the onboarding overlay and the recovery prompt it does nothing at all. No key reaches the stop, because every global shortcut is inert while a modal is mounted. When a stop is unconfirmed or fails, the only record is a console line, and the console is closed by default. And while the machine may be moving, the Help menu's Welcome Guide can reload the whole window, and the file menus can open native dialogs that may take the window. This plan makes STOP clickable above every overlay. It gives STOP two keys that work in every Kerf dialog and text box whenever the keystroke reaches Kerf; an input method or the system can take a key first, and the plan names where. The stop's outcome shows in the job bar the moment STOP is pressed, and it is replaced when the controller answers. "Stopped" shows only when Kerf can tie the answer to this stop and has sent nothing since. Kerf opens a native or blocking dialog only when it has fresh evidence the machine is idle with nothing in flight and knows its own last instruction to the laser was off (unknown counts as on), and while one is open it sends no job, line or motion byte. Nothing is added ahead of the reset byte.

**Key decisions.**
1. **STOP is raised in place, not portalled.** The STOP button and its outcome line get `position: relative` and `zIndex: STOP_LAYER_Z` (1,000,000, one exported constant). No dialog file is edited. A source scan plus a runtime walk make every other z-index stay below it, and they ban the browser top layer. This needs no A3.
2. **One operator stop function.** `operatorStop()` holds `handleStop`'s three statements, moved verbatim (`JobActionBar.tsx:110-112`). The button, both Stop keys and a new STOP on the crash screen all call it.
3. **Two Stop keys: Ctrl+. (⌘. on macOS) and Shift+Esc** (D1 recommendation). Both are matched in one window capture-phase listener installed at module load in `main.tsx`, so they keep working after a React crash replaces the UI. The listener ignores auto-repeat. **Revision 3 drops the composition veto** (critic F3): a chord the page receives during IME composition is one the input method did not take, so it stops. A key the input method takes arrives as `key: "Process"` or not at all, and no matcher can recover it. The public claim is narrowed to match (Design C). It is a no-op exactly when the button is disabled (`!machineConnected`).
4. **The stop outcome is written after the stop is dispatched, never before.** Outcomes are grouped into episodes. An uncertain answer settles its episode at once; `confirmed` waits for every answer. **Revision 3 adds three conservative conditions for "Stopped"** (critic F2): no other command that can run a native stop overlapped the episode (the episode is then *tainted*); no job, line or motion byte has been requested since the press (the episode is then *superseded*, and "Stopped" is never shown for it); and the connection is a real one (never connection 0). Kerf does not get a native operation id. It infers identity from a fact pinned by a scan of the Rust source: every production caller of the native stop runs inside one of five commands TS invokes, and TS now tracks all five through one seam. The 7 s watchdog is a UI policy deadline, not a bound on native (critic F6).
5. **Outcome writes are transactional, with an independent failsafe** (critic F4). Each entry point computes its next state with no side effects, then commits it, then publishes. Any fault in any of the three, or in the watchdog callback, ends in a visible uncertain message drawn straight into the page by `stopFailsafe.ts`, outside React and the store, and makes the connection's later outcomes at most uncertain. Attempt records are capped at 32.
6. **STOP looks live in every state where motion is possible.** A7's solid rule is extended with `motionPending` and with any stop that is pending or uncertain.
7. **A blocking dialog needs positive evidence of quiescence and of commanded-off output** (round-2 F1, round-3 F1). Kerf may open a native dialog, `confirm` or reload only when the machine is disconnected with nothing in flight, or connected and idle, fresh, proven idle by a status query dispatched after the last command settled, with no command in flight, no job session, no job flag, no `motionPending`, no pending or uncertain stop, **and the laser commanded off**. Commanded output is tracked at the one place every output-commanding byte passes (Diagnosis 10). Any line with M3, M4 or a positive S word, any resume byte, and every new connection set it to *maybe on*. Only an acknowledged M5 requested after the last on, a confirmed reset Kerf can tie to its own stop, or a connection that printed a GRBL banner set it *off*. An Idle report never clears it, and neither does the `A:` field (DECISIONS 2026-09-25). Disconnect sends the stop reset while it is maybe on (D2). While a guarded dialog is open, every job, line and motion byte is refused. Each command is reserved in the ledger before any listener runs, so a synchronous subscriber cannot open a dialog in the gap (round-3 F2). Every blocking call goes through `src/lib/blockingDialog.ts`, enforced by syntax-aware lint rules with bypass fixtures, whose limits are stated (round-3 F3).
8. **No native change.** `serial_stop`, the fence, the submit lock and the single-reset contract are untouched. Every statement that runs before the dispatch today stays byte-identical, and so does their order.
9. **Five batches.** B1a (outcome core, activity ledger, failsafe) and B2 (the stop function, the keys, the crash screen) share no file and can run in parallel. B1b (wiring the ledger into the machine modules) waits on B1a. B3 (the raised STOP and the outcome line) waits on A1, A7, B1a, B1b and B2. B4 (the dialog seam) waits on A2, A10, B1b and B3. ### 2. Sidebar and job bar stacking

STOP paints at `z-index: auto` in the root stacking context. Nothing between it and the root creates a stacking context. The App root is `position: relative` with no z-index (`App.tsx:221-233`, :231). The main row is `display: flex; overflow: hidden` (:263). ### 4. The stop path, end to end

1. **JobActionBar** `handleStop` (`JobActionBar.tsx:105-113`): `stopActiveSession()` (not awaited), `setJobRunning(false)`, `await machineConnection.emergencyStop()`. The comment at :106-109 calls the order safety-critical.
2. `stopActiveSession` (`jobSession.ts:243-262`) runs synchronously up to `await session.settled`: `cancel()` and a new `stoppingPromise`.
3. `setJobRunning(false)` notifies zustand subscribers synchronously. One of them is keep-awake's (`keepAwake.ts:47-65`), which on true→false calls `invoke("keep_awake_release")` (:59-63). **So on every STOP during a job the first IPC posted is `keep_awake_release`, and `serial_stop` is second.** `keep_awake_release` is an async command that does its work in `spawn_blocking` (`src-tauri/src/commands/power.rs:75-87`), so the stop is not queued behind it. The other subscriber is connection.ts's poll-suspend flag (`connection.ts:531-533`).
4. `emergencyStop` (`connection.ts:960-994`): `provisionalRevoke()` (store write, :962, body :86-88), `addConsoleLine("Emergency stop initiated")` (:963), then `invoke("serial_stop")` (:966-973). `@tauri-apps/api` 2.10.1's `invoke` is an async function whose body calls `window.__TAURI_INTERNALS__.invoke` synchronously (`node_modules/@tauri-apps/api/core.js:201-203`). The IPC is therefore posted before `emergencyStop` first yields, and before React re-renders anything. Because `invoke` is an async function it never throws synchronously; any failure arrives as a rejection. `serial_stop` takes no `conn` by design (the test helper `src/lib/machine/__tests__/setupConnInvoke.ts:9` lists the conn-carrying commands; motion trust exempts `0x18`).
5. Native `serial_stop` (`src-tauri/src/commands/serial.rs:1587-1592`) runs `serial_stop_inner` (`:1393-1582`) in `spawn_blocking`. The steps are: read `epoch_before` (`:1395`); single-flight `StopGuard` (`:1398`); close admission under `submit` (`:1432-1437`); invalidate the snapshot and set `job_abort`; clear `banner_observed`; write `0x18` on the realtime handle with one retry (`:1455-1482`), each successful write followed by `port.flush()` (`:1465`, `:1472`); wait up to 3 s for a banner (`:1504-1537`), each pass of which may block in `read_until` (`:1518`) before the deadline is checked again.
6. Outcomes (`StopResult`, `src-tauri/src/commands/serial_session.rs:129-146`, serde tag `outcome`): `confirmed {epochBefore, epochAfter, messages}` (banner seen; epoch incremented; phase Idle by CAS, `serial.rs:1539-1554`); `submittedUnconfirmed {epoch, messages}` (no banner in 3 s, or a concurrent disconnect moved the phase; phase Unknown, `:1555-1577`, the store at :1569); `submissionFailed {epoch, error, messages}` (both writes failed or no port; phase Unknown, `:1484-1497`, the store at :1493). Every message says beam state is unqualified.
7. TS (`connection.ts:978-993`): each message goes to the console, as an error on `submissionFailed` and a warning otherwise. On `submissionFailed`, `setMachineState("alarm")` (:983-985). On an IPC rejection, or a reply whose `messages` cannot be iterated, `setMachineState("alarm")` plus "E-stop send failed: … use the machine's physical stop." (:986-993). **Neither write checks the connection**, so a late failure from an earlier connection sets alarm on the current one.
8. Other callers of `emergencyStop`: `pauseJob` (`jobStream.ts:47-57`; Pause is stop), the stream's error and abort paths (`jobStream.ts:318`, :456), and `disconnect()` with a job or a run/hold state (`connection.ts:604-614`, awaited before teardown).

**Who can own a native stop (revision 3, critic F2).** `serial_stop_inner` has exactly four production callers, all in `serial.rs` before its first test module (`#[cfg(test)] mod tests` at :1686): `serial_stop` (:1590); `serial_stream_job_inner` after an event-sink failure (:1291); `serial_abort_job` (:1375); and `disconnect_inner_with_job` (:487), which is reached from `serial_disconnect` (:460) and from `serial_connect_inner` when a connection is already live (:335-337). No other `.rs` file calls it outside test files (grep of `src-tauri/src`, 2026-10-04: the other hits are `serial_trust_tests.rs`, a test module mounted under `#[cfg(test)]` at :5077-5079). So every native stop runs inside one of five commands TS invokes: `serial_stop`, `serial_stream_job`, `serial_abort_job`, `serial_disconnect` and `serial_connect`. TS invokes them at `connection.ts:966-973`, `jobStream.ts:228`, `connection.ts:878` (inside `abortJob`, which nothing calls), `connection.ts:638` and `connection.ts:483`. The native command runs strictly inside the interval between TS posting it and TS seeing its promise settle. That containment is what Design D uses in place of a native operation id.

**The joiner can report an earlier stop.** A second `serial_stop` while one is in flight is a joiner. It polls for up to 3 s (`serial.rs:1403-1408`), then `take()`s `last_stop` (`:1409-1413`), or falls back to `submittedUnconfirmed` "joined existing stop operation". `last_stop` is written at the end of every stop (`:1494`, `:1579`) and never cleared at the start of one. It lives in the one `SerialSession` the app keeps for its whole run (`serial.rs:180`; `serial_session.rs:202`, :237). An owner whose banner wait runs the full 3 s outlasts a joiner that arrived within a few ms of it. That joiner then returns the previous stop's result as its own: possibly `confirmed`, possibly from an earlier connection, possibly from a native stop TS never saw the result of. TB1 handles this in TS (Design D) without touching native, and parks the native fix.

**A delayed reply can describe a stop that is already history** (revision 3, critic F2). Native sets phase Idle before the confirmed result is returned (`serial.rs:1539-1554`), and `serial_job_begin_inner` admits a job from Idle (`:1617-1631`, the check at :1618). So a stop can finish natively, its reply can still be in flight, and a new job or jog can be admitted in that gap. The reply then arrives describing a reset that happened before the new activity.

**The TS epoch watermark is not monotonic.** The native epoch is: it starts at 0 (`serial_session.rs:231`) and is incremented at connect (`serial.rs:405`), on a confirmed stop, and at disconnect (`:519`), and is never stored. But `resetStatusConsumer()` (`machineStatus.ts:283-287`) zeroes TS's accepted-snapshot watermark (`lastEpoch`, written at :191) at connect (`connection.ts:497`) and at disconnect (`:644`). So until the first status report is accepted on a connection, the snapshot half of any floor reads 0. Every real snapshot on a live connection has epoch 1 or more, so a watermark of 0 means "none accepted since the last reset".

### 6. Stored states and STOP today

`machineStateToStore` maps jog and home to `run` and GRBL's unknown to `alarm` (`machineStatus.ts:99`, :103, :107; unreachable fallback `alarm` at :109). Check and sleep map to idle. A new connection starts stale (`store/index.ts:674`). `motionPending` defaults false (:204). It is set provisionally on every motion send, consoled moves included (`connection.ts:668`, :83-85; `isMotionCommand`, `jogBounds.ts:121-131`), and then mirrored from native snapshots (`machineStatus.ts:251`). **Native's `motion_pending` counts sends, not motion** (revision 3, critic F1): `motion_enter` increments it before the `command` wait (`serial_session.rs:714-721`), and `MotionGuard`'s drop decrements it when the send returns (`:594-606`). A jog's send returns at its `ok`, while the head is still moving. So an accepted snapshot can report `run` with `motionPending: false`, and `jobRunning` is false for a jog. A stationary Fire (`M3 S…`, `G4 P0.5`, `M5`, three awaited sends, `MachinePanel.tsx:1128-1130`) is not a motion command. So the store can read idle while the head moves (the jog window) or while the beam is commanded on (Fire). ### 9. What a blocking dialog must not overlap (revision 3, critic F1)

Revision 2's guard was `jobRunning || motionPending`. That admits three hazardous states. ### A. Raised in-place STOP or a portal STOP surface

**Chosen: raised in place.** It is the smallest change that keeps one control, one handler and A7's presentation. Its one structural risk, an ancestor stacking context, is detectable both by a test and by a real hit-test, which the browser check runs at the base and head revisions named in Verification 5. The portal is not rejected categorically. It wins if the browser check finds a stacking context on STOP's ancestors that cannot be removed (for example a WebKit-specific compositing rule). Then B3 stops, and portal (ii) is the fallback, re-planned and re-critiqued. **A future surface that needs the top layer is a different problem** (revision 3, correcting revision 2, critic inversion): neither design survives the top layer, so such a surface needs its own top-layer-aware stop surface with input and focus proof, not a higher body z-index. The scan's top-layer ban stands until that plan exists. Under every design the focus contract is identical, as the row above shows: pointer access to STOP is never a focus-trap question, because the traps are keyboard-only, and keyboard access is the Stop keys.

**Raised whenever enabled, not only in motion states.** A conditional raise ("only while running, held, stale…") would make reachability depend on Kerf classifying the machine's state correctly. That classification is exactly what is uncertain here: Fire is not a motion command, a consoled move sits in the jog window, and a stale status reads idle. The z-index is unconditional. The cost is the corner overlap at windows narrower than about 1240 px. There STOP covers part of a large dialog's bottom-right corner, and a click meant for that corner can reset the controller (a lost job or lost homing, not a hazard). The browser check measures it at 1000 × 600, and the Parking Lot carries the follow-up.

### D. The stop outcome

**Where it is written.** Only in `emergencyStop`, so every stop shows: the button, the keys, the crash screen, Pause, the stream's own abort, and `disconnect()`. The target shape (B1b) changes nothing before the dispatch:

```ts
async emergencyStop(): Promise<void> {
  const store = useStore.getState();                                    // unchanged
  provisionalRevoke();                                                  // unchanged
  store.addConsoleLine("Emergency stop initiated", "warning");          // unchanged
  let attempt = 0;                                                      // bindings only, no work
  let sentOn: number | null = null;
  try {
    const reply = invoke<StopResultWire>("serial_stop");                // dispatch, unchanged position
    sentOn = connId;                                                    // TB1: first statement after dispatch
    stopCapableBegin();                                                 // ledger count; integer only, cannot throw
    attempt = beginStopAttempt(sentOn);                                 // total
    const result = await reply;
    for (const msg of result.messages) { /* unchanged console lines */ }
    settleStopAttempt(attempt, sentOn, connId, result);                 // total
    if (result.outcome === "submissionFailed" && sentOn === connId) store.setMachineState("alarm");
  } catch (e) {
    if (attempt) settleStopAttempt(attempt, sentOn, connId, { rejected: String(e) });   // total
    if (sentOn === null || sentOn === connId) store.setMachineState("alarm");
    store.addConsoleLine(`E-stop send failed: ${String(e)}. …`, "error");   // unchanged text
  } finally {
    if (sentOn !== null) stopCapableEnd();                              // pairs with stopCapableBegin
  }
}
```

No other JS runs between the `invoke(...)` call and `sentOn = connId`, so `sentOn` is the connection the dispatch was made on. The alarm guard is computed here, from `sentOn === connId`, and not from anything `stopOutcome.ts` returns. It guards both alarm writes, which is today's §4 step 7 defect. `sentOn === null` can only mean the dispatch line itself failed before assignment, which `invoke` being an async function rules out (§4 step 4); it then keeps today's unconditional alarm. With the connection unchanged (both 0 when disconnected, as in the existing tests) the alarm is written exactly as today. `serial_stop` is the one stop-capable command that does not go through the ledger's `invokeStopCapable` wrapper, because the wrapper would add work before the dispatch; it is counted by the two calls around it instead.

**`src/lib/machine/activityLedger.ts` (new, B1a; wired in B1b).** A small module of counters, a commanded-output record and listeners, with no store writes of its own. It is the one seam both Design D and Design G read.
- **The wrappers.** `invokeActivity(cmd, args)` is the only path for `serial_send`, `serial_send_byte` and `serial_job_begin`. `invokeStopCapable(cmd, args)` is the only path for `serial_abort_job`, `serial_disconnect` and `serial_connect`. `serial_stream_job` is both kinds and goes through `invokeActivity(cmd, args, { stopCapable: true })`. An *admission* is every `serial_send`, every `serial_send_byte` except `0x18`, `0x85`, `0x21` and `?`, `serial_job_begin` and `serial_stream_job`.
- **The order: one synchronous run, with no `await` before step 5** (revision 4, round-3 F2).
  1. *Re-entry check.* If a ledger listener is running (`inListener`) and the command is an admission, return a rejected promise, `refused: reentrant: Kerf did not send this because it was issued while Kerf was updating the stop display.` Nothing is reserved. No current subscriber sends machine commands; this makes a future one fail loudly instead of reordering the wire.
  2. *Exclusion check.* If a guarded blocking surface is open and the command is an admission, return a rejected promise, `refused: blocking-dialog: A file dialog is open. Close it before starting a job or moving the machine.` That is the `refused:` prefix native uses, so `send()`, `beginJobSession` and `jobStream` already route it as a refusal (`connection.ts:715-720`, `jobSession.ts:59-62`, `jobStream.ts:287-293`). Nothing is reserved.
  3. *Reserve*, plain assignments only: raise the in-flight count (and the stop-capable count, for the combined wrapper), raise the generation, take the request's sequence number, and apply the command's on effect (below). From here, `machineQuiescent()` is false and `tryBeginBlocking` refuses.
  4. *Listeners*, with `inListener` set and each in its own `try`/`catch`: the supersede listener for an admission, then the taint listener for a stop-capable command. Supersede publishes to the store, whose subscribers run synchronously inside this step. They see the reservation already in place.
  5. *Post*: `invoke(cmd, args)`, before any `await`, so the IPC is posted in the same task as before. `invoke` is an async function and cannot throw synchronously (§4 step 4); the call is still wrapped, so a synchronous throw becomes a rejection.
  6. *Settle*, exactly once, in `finally`: apply the result's off effect (below), lower the counts, raise the generation.

  `invokeStopCapable` runs the same steps without step 2 (a connect or disconnect is not an admission), with only the taint listener. `stopCapableBegin()` and `stopCapableEnd()` reserve and release the count for `serial_stop`, whose `invoke` must stay first in `emergencyStop`. `emergencyStop` is never refused, re-entrant or not.
- **Why this is mutual exclusion.** A blocking surface begins only in `tryBeginBlocking(isQuiescent)`, which in one synchronous call checks that nothing is reserved or open, evaluates the predicate, and sets the flag. It calls nothing that could publish. An admission reserves in step 3, before any code outside the ledger runs. JavaScript runs one of the two at a time. So either the admission's step 2 sees the surface open and refuses, or `tryBeginBlocking` sees the reservation and refuses. Steps 1 to 3 and `tryBeginBlocking` call nothing external, so there is no third point at which the other can run.
- **Commanded output** (revision 4, round-3 F1). The ledger keeps two sequence numbers, `lastOnSeq` and `lastOffSeq`, and `outputMayBeOn()` is `lastOnSeq >= lastOffSeq`. They start at 1 and 0, so unknown counts as on.
  - *On*, at reservation (step 3), setting `lastOnSeq` to the request's number. A `serial_send` line which, upper-cased with all whitespace removed (GRBL ignores spaces), contains `M` then `3` or `4` with any leading zeros and no further digit; or which does not start with `$` and contains an `S` followed by a number that is not zero or does not parse. A `serial_send_byte` other than `0x18`, `0x85`, `0x21` and `?`. A `serial_stream_job` whose text matches the line rule anywhere. Every `serial_connect`. Comments are not stripped for this rule, so `(M3)` counts as on; that over-counts on purpose.
  - *Off*, at settlement (step 6), setting `lastOffSeq` to the request's own number, so any later on request still wins. A `serial_send` whose line, with `;…` and `(…)` comments removed, upper-cased and stripped of whitespace, is exactly `M5` (or `M05`, optionally after an `N` number), and whose result carries the current connection's id, contains `ok`, and has no line starting `error:` or `ALARM`. A `serial_stream_job` that resolves `complete` on the current connection, whose text's last spindle word (`M3`, `M4` or `M5`) is `M5`. A `serial_connect` whose banner starts `Grbl ` (`serial_pump.rs:112-113`'s rule). And `noteResetConfirmed(pressSeq)`, which `stopOutcome` calls only when an episode's view becomes `confirmed` (fresh, untainted, unsuperseded, this connection), with the sequence number taken at that press. A superseded episode never confirms, so a reset never clears an M3 sent after the press.
  - *Never off*: any status report, Idle included; `S0`; `M2` or `M30`; `softReset`'s unconfirmed `0x18`; the `A:` field; a stop whose view is uncertain or cleared; a disconnect.
  - What "off" means: Kerf's last instruction to the laser was acknowledged as off, or a reset banner was seen after it. It is commanded state, not beam state (the status-only ruling; DECISIONS 2026-09-05 records a `0x18` that did not stop the beam). The copy still sends the operator to check the laser.
- Status evidence: `activityGeneration()`; `noteStatusReport(genAtDispatch, idle)`, called by `pollStatus`; `idleProven()`, true only when the last fresh `report` was idle, was dispatched at the current generation, and nothing is in flight.
- Blocking surfaces: `tryBeginBlocking(isQuiescent)`, `blockingEnd()`, `blockingOpen()`.
- **Tracked state is bounded; outstanding requests are not throttled** (revision 4, round-3 F7; revision 3's "memory is bounded whatever happens" is withdrawn). The ledger holds integers and two sequence numbers, and `stopOutcome` holds at most 32 attempt records and one timer (below). That is all TB1 bounds. It does not bound, and must not throttle, what each STOP press creates outside that state: one pending JS promise until its `invoke` settles, and one native `tokio::task::spawn_blocking` task per `serial_stop` (`serial.rs:1587-1592`). A joiner returns within about 3 s by construction (:1403-1413); an owner can block in `flush()` or `read_until` (:1465, :1472, :1518). Tokio's default cap on blocking threads is 512 ([tokio `Builder::max_blocking_threads`](https://docs.rs/tokio/latest/tokio/runtime/struct.Builder.html#method.max_blocking_threads)); whether Tauri's runtime changes it is not checked. Past the cap, further stops wait for a thread, and joiners free theirs within 3 s. B1b measures the TS side: 1000 presses that never resolve each post exactly one `serial_stop`, and the ledger and the record map stay at their bounds. The native task count under a hung owner is a residual on the hardware path that TB1 does not measure.

**`src/lib/machine/stopOutcome.ts` (new, B1a)**, a state machine whose view lives in the store as `stopOutcome: StopOutcomeView | null` (runtime only: `toProject()` does not read it, `fileOps/index.ts:507`, `autoSave.ts:40`):

```ts
type StopPhase = "pending" | "confirmed" | "uncertain";
interface StopOutcomeView { readonly episode: number; readonly connId: number; readonly phase: StopPhase; readonly overdue: boolean; readonly fault: boolean; }
```

- **Episode.** `beginStopAttempt(conn)` returns a new attempt id. The attempt joins the current episode if its view is `pending`, not overdue, not superseded, and on the same `conn`. Otherwise a new episode starts: view `pending`, the floor and its "known" flag sampled, and the watchdog armed. A press after the watchdog has fired, or after the operator has asked for new activity, starts a new episode.
- **Settle early on uncertain; confirmed waits for all.** Any `uncertain` answer settles the episode as `uncertain` at once and clears its watchdog. That is final. A `confirmed` answer is only recorded. When every tracked attempt has answered `confirmed`, the view is decided by the rules below.
- **Classification of one answer.** `confirmed` only if `outcome === "confirmed"`, `epochAfter` is a finite number, the floor was known when the episode began, `epochAfter > floor`, and `sentOn === connNow === episode.connId !== 0`. A result whose `sentOn` differs from `connNow` changes neither the view nor `machineState`; its console lines still append and its `epochAfter` still raises the floor. Everything else is `uncertain`: `submittedUnconfirmed`, `submissionFailed`, an IPC rejection, an unknown outcome string, a malformed reply, a replay at or below the floor, and any `confirmed` in an episode whose floor was unknown.
- **When every answer is confirmed** (revision 3, critic F2), in this order:
  1. **Superseded: the view is cleared, never confirmed.** An episode is superseded when the ledger reports an admission request (a line, a non-reset byte, a job begin, a stream job) after the episode began. The listener runs synchronously before that command's `invoke`, so it is marked before native can admit anything. A delayed reply then cannot put "Stopped" above a newer job or jog: the critic's schedule (stop finishes natively, reply delayed, new job admitted, reply lands) clears the line instead. An `uncertain` answer still shows the uncertain line, because that warning is never wrong to show.
  2. **Tainted: the view is `uncertain`.** An episode is tainted if any stop-capable command other than its own attempts was outstanding at any moment while it had an attempt outstanding: checked at each `beginStopAttempt` (`stopCapableCount() − 1 − own outstanding > 0`) and on every `invokeStopCapable` start while it has attempts outstanding. Because every native stop owner runs inside a command the ledger counts (§4, "Who can own a native stop"), an untainted episode's attempts were either the native owner or joined an owner that is also in the episode. The minimum then guarantees that owner's own fresh answer is among those all classified `confirmed`. An episode begun on connection 0, or one with an attempt beyond the record cap, is tainted from birth.
  3. **Faulted: the view is `uncertain`**, for the rest of the connection (below).
  4. Otherwise `confirmed`.
- **The floor stays a secondary rule.** `floor` is the max of every `confirmed` `epochAfter` received (dropped ones included) and the accepted-snapshot watermark (`machineStatus.ts:191`, through a new getter `acceptedSnapshotEpoch()`). If that watermark is 0 when the episode begins, the floor is unknown and every `confirmed` in it classifies `uncertain` (the first status interval after connect, §4). Snapshots and stop results share `session.epoch` (`grbl_status.rs:100-102`; `serial.rs:1395`; `serial_session.rs:275-277`).
- **The residual revision 2 stated is closed, not listed.** Revision 2 conceded that a native-internal stop after the last snapshot could leave an unseen `confirmed` that a joiner replays while a stalled native owner sits outside the TS episode. That owner now runs inside a counted command, so the episode is tainted. What remains is a precondition, not a residual: a future native caller of `serial_stop_inner` outside the five commands would break the inference. `stopIdentityScan.test.ts` (B1b) fails the suite when the production caller set changes, and the B1 DECISIONS pin makes that change an amendment. The native fix (an operation id, or a joiner that accepts only a result written after it joined) stays parked; if it lands, the inference becomes a cross-check.
- **Native identity, compared** (round-3 inversion). A native operation id would replace taint, the floor and the Rust caller scan with one check. It needs edits to `serial_stop_inner` and its result type, a change to the golden `src-tauri/tests/golden/stop_result_fixture.json`, and its own plan and critic, inside the fence code the 2026-09-24 ruling protects. TB1 keeps the inference because it leaves that code untouched, and every rule in it only withholds "Stopped". When the parked native fix lands, its plan should retire taint and the floor rather than add to them.
- **Connection identity and lifetime.** `stopConnectionEnded(conn)` is called from `disconnect()` right after `connId = 0` (`connection.ts:636`), with the old id: a `pending` view on that connection becomes `uncertain` and its watchdog is cleared. `stopConnectionStarted(conn)` is called from `connect()` right after `connId = connected.connId` (`:488`): it clears any view from another connection, drops every attempt record, clears the fault flag and hides the failsafe. The ledger's stop-capable count is not reset there, because it counts real IPCs that may still be running. `stopJobBegan()` is called from `beginJobSession` after a session is created (`jobSession.ts:65-66`; the only door for job, frame, material test and its frame, `JobActionBar.tsx:72`, :143, `MaterialTestDialog.tsx:240`, :263). It clears a settled view and never a pending one; native admitted that job only from phase Idle (`serial.rs:1618`), which no unconfirmed or failed stop leaves (`:1493`, `:1569`). A newer stop replaces the view. Loading a project or New does not touch it.
- **A STOP mid-disconnect.** Between `connId = 0` (`connection.ts:636`) and `setMachineConnected(false)` (`:639`), while `serial_disconnect` is awaited (`:638`), STOP is still enabled. A press there dispatches with `sentOn` 0. Revision 3 makes that episode tainted from birth (connection 0) and the in-flight `serial_disconnect` taints it too, so it can show `pending` and then `uncertain`, never "Stopped". The existing alarm-at-conn-0 behaviour is kept, as `connection.test.ts` pins.
- **Watchdog, replacement-safe.** `STOP_OVERDUE_MS = 7000`. **This is a UI policy deadline, not a bound on native** (revision 3, critic F6; revision 2's "exceeds native's own worst case … about 6.05 s" is withdrawn). Native's realtime write, its `port.flush()` (`serial.rs:1465`, :1472) and its banner loop's blocking `read_until` (:1518) are not bounded by anything this plan can cite, and the plan itself names a hung drain (Physical failure outcomes). So a native stop can outlast 7 s, and the watchdog then shows the uncertain wording, which is the safe direction. One timer per current episode, holding the episode id. When it fires it writes only if the view is still that episode and still `pending`, and then it sets `overdue: true`. Settling, clearing, a new episode and a connection end all clear it. A late answer for the same episode still settles an overdue view by the rules above. The view stays until replaced or cleared; nothing auto-hides it.
- **Bounded retention** (critic F4, X8). Attempt records exist only while outstanding, in one map capped at `MAX_TRACKED_ATTEMPTS = 32` across episodes on the connection. An episode keeps counts, not a list. A press beyond the cap is still dispatched (nothing ever refuses a stop) and gets an id, but it is untracked: its episode is tainted and its answer changes no view. Records are deleted on answer and all dropped at `stopConnectionStarted`. At most one watchdog timer exists at any time.

**Transactional writes and the failsafe** (revision 3, critic F4; revision 2's "a fault leaves the view exactly as it was" is withdrawn).
- **Ordering.** Every entry point (`beginStopAttempt`, `settleStopAttempt`, the supersede and taint listeners, the watchdog callback, the three lifetime hooks) does three steps. *Compute*: `next = reduce(state, event)`, a pure function over an immutable copy. If it throws, nothing has changed. *Commit*: `state = next`, then reconcile the one timer (plain assignment and `clearTimeout`/`setTimeout`). *Publish*: `useStore.getState().setStopOutcome(viewOf(next))`. Zustand assigns the new state before it calls subscribers, so a throwing subscriber leaves the store updated but later subscribers, React's included, possibly un-notified. A stale "Stopped" can therefore stay on screen after a fault in any step.
- **Fault path, the same for every step and for the watchdog callback.** `stopFault(where, err)`: (1) `console.error` once; (2) set the connection's `faulted` flag, so every later view on this connection is at most `uncertain`; (3) `showStopFailsafe()` (below); (4) a best-effort `setStopOutcome({ …, phase: "uncertain", fault: true })` inside its own `try`/`catch`. `beginStopAttempt` returns 0 after a fault and `settleStopAttempt` returns nothing, so neither throws into `emergencyStop`, and the console lines, the alarm write and the rejection text are never skipped.
- **Which connection owns a fault** (revision 4, round-3 F4). A fault belongs to the connection of the event being processed: an answer's `sentOn`, a watchdog's episode connection, a lifetime hook's argument. If that is the current connection, or connection 0 (a press mid-disconnect, with no newer connection to protect), the fault path above runs in full. If it is an earlier connection (an answer whose `sentOn` is not `connNow`), the fault is logged once and nothing else happens: no flag on the current connection, no banner, no store write, and the floor is not raised. That is safe because a foreign answer changes no view (above), its processing publishes nothing, and its compute step is pure, so a throw there leaves the module state as it was. The earlier connection's view was already made uncertain by `stopConnectionEnded` and cleared by `stopConnectionStarted`. A fault inside `stopConnectionStarted` belongs to the new connection.
- **`src/lib/machine/stopFailsafe.ts` (new, B1a).** It owns `STOP_LAYER_Z` (B3 imports it from here). `showStopFailsafe()` creates or reuses one `<div id="kerf-stop-failsafe" role="alert">` appended to `document.body`, with inline styles only (fixed, top 0, full width, `pointer-events: none`, `z-index: STOP_LAYER_Z`, A1's danger colours with literal fallbacks), and sets its text with `textContent`. It touches no React node and reads no store. It is visible above every dialog, never takes a click, and never covers STOP, which is at the bottom of the sidebar. `hideStopFailsafe()` removes it, called only from `stopConnectionStarted`. If `document.body` is missing, it does nothing; nothing then reaches the screen, and that case is the crash-screen and e-stop path. It uses `role="alert"` because it exists only after a fault; `machineJobLoop.test.tsx`'s single-alert query never runs with a fault.

### G. A blocking dialog only from proven idle with output commanded off, and nothing admitted while one is open (revision 3 and revision 4)

**`src/lib/blockingDialog.ts` (new, B4) is the only door.** It is the one file in `src` (outside tests) allowed to name `@tauri-apps/plugin-dialog`, `plugin:dialog`, `confirm`, `alert`, `prompt` or a page-discarding `location` call. It exports:
- `open`, `save` and `message`, with the plugin's own signatures, so callers change only their import. - `reloadForWelcomeGuide(isDirty, reset)`: if `!tryBeginBlocking(machineQuiescent)`, `refuse("welcomeGuide")` and return. If dirty, `window.confirm("You have unsaved changes. - `refuse(kind)`: writes the cause's string for the kind (Copy ledger) with `setStatusMessage` and as one console warning. **`machineQuiescent()`, the invariant** (exported for tests; reads `useStore.getState()`, the ledger and `jobSessionBusy()`):

```ts
quiescent =
  inFlightCount() === 0 && stopCapableCount() === 0 && !blockingOpen() && (
    !s.machineConnected ||
    ( s.machineState === "idle" && !s.statusStale && !s.jobRunning && !s.motionPending
      && s.stopOutcome?.phase !== "pending" && s.stopOutcome?.phase !== "uncertain"
      && !jobSessionBusy() && idleProven()
      && !outputMayBeOn() ));                        // revision 4: commanded output
```

Each clause, and the hazard it closes:
- `inFlightCount() === 0`: no line, byte, job begin or stream job is between TS posting it and seeing it settle. This is the in-flight admission half of critic F1 (§9 c), and it covers Fire: its three sends are awaited back to back (`MachinePanel.tsx:1128-1130`) with no task boundary between one settling and the next being posted, and the generation moves at each.
- `stopCapableCount() === 0`: no stop, connect or disconnect in flight. With the `stopOutcome` clause, this is post-STOP uncertainty (§9 b): STOP followed at once by Welcome Guide is refused.
- `machineState === "idle"`, `!statusStale` and `idleProven()`: positive evidence. `idleProven()` needs a fresh `report` status, dispatched at the current ledger generation, that stored idle (§9). This is running-with-pending-false (§9 a): a jog whose send has returned is refused until a poll posted after that return reports Idle, and a poll posted before it, answered after, does not count. Hold, door and alarm are refused. Alarm is refused because the store cannot tell GRBL's locked Alarm from GRBL's unknown state (both store as alarm, `machineStatus.ts:100`, :107); the cost is that file dialogs wait for Unlock or Disconnect after an alarm (R12, Parking Lot).
- `!jobRunning`, `!motionPending`, `!jobSessionBusy()` (a session exists or is still stopping, `jobSession.ts:29`, :33): belt and braces for the windows the ledger already covers, kept because each is cheap and each is an independent source.
- `!outputMayBeOn()` (revision 4, round-3 F1): Kerf's last instruction to the laser is an acknowledged off (Design D, "Commanded output"). This is what an Idle report cannot show. A console M3 answered `ok` and followed by a fresh Idle report is refused, and so is a Fire whose `M5` failed, until an acknowledged `M5`, a confirmed stop, or a reconnect that printed a GRBL banner. A successful Fire ends with its `M5` acknowledged, so it opens dialogs again as today once a fresh poll reports Idle. The "positive evidence" of the other clauses is evidence about motion only; this clause is the separate evidence about commanded output, and it is commanded state, never beam state.
- Disconnected with nothing in flight is allowed, whatever `outputMayBeOn()` says: there is no connection for Kerf to stop through, STOP is disabled, and a dialog takes nothing away. Disconnect itself now sends the stop reset first when output may be on (B1b, D2), so a deliberate disconnect does not leave a commanded beam behind.

**Lifetime exclusion.** While a guarded `open`, `save` or `message` is awaited, `blockingOpen()` is true and the ledger refuses every admission (Design D, step 2), and the reverse holds because an admission reserves before any listener runs (step 3). So no job begins, no line or motion byte is written, and no stream starts until the dialog closes. STOP is never refused: `serial_stop` does not go through `invokeActivity`, and `0x18` and `0x85` bytes are exempt. With the entrance invariant, this closes the case revision 2 parked: a dialog opened while idle, with a job then starting under it. It also closes round 3's re-entry schedule: a store subscriber that runs during a send's supersede and tries to open a dialog finds the send already reserved, and is refused.

The nine call sites are unchanged, and each already treats `null` or `'Cancel'` as the operator cancelling (New, Open and Open Recent stop; Save As returns false). `MaterialLibrary.tsx`: the two `await import("@tauri-apps/plugin-dialog")` lines (:115, :131) import `../../lib/blockingDialog` instead. `MenuBar.tsx`: the Welcome Guide action (:432-441) becomes `() => reloadForWelcomeGuide(useStore.getState().isDirty, resetOnboarding)`. ### Physical failure outcomes (software cannot certify beam extinction)

Kerf's best evidence is that the controller printed a reset banner after Kerf wrote `0x18`. That is what "confirmed" means, and no software state proves the beam is dark. Named failure outcomes, each with what Kerf shows:
- **The reset reaches the controller and the beam or motion does not stop.** DECISIONS 2026-09-05 records a `0x18` that failed to stop the beam on 2026-09-02 on the owner's vendor fork. Kerf may even show "confirmed". The confirmed line therefore tells the operator to check, and only the machine's e-stop is the stop.
- **The reset never reaches the wire.** A wedged USB adapter (`POLLOUT` reported, URBs not completing; Parking Lot, the stop's Step 5 `tcdrain`), a pulled cable, or a dead port. The result is `submissionFailed`, `submittedUnconfirmed` after 3 s, or a hang past 7 s (native's flush and read are unbounded here, Design D): the uncertain line.
- **The controller keeps executing what it already holds.** Up to the 127-block planner, and the 65,536-byte receive buffer in buffered mode (`[OPT:VHL,127,65536]`, DECISIONS 2026-09-05). The one admitted job line before the stop may run (ARCHITECTURE, Admission fence residuals). Console, Fire and settings writes are not phase-gated natively and can land after a stop (ARCHITECTURE residuals; Parking Lot); each such send now supersedes the stop's line, so "Stopped" is never shown over one.
- **The laser-switch wedge** (open, DECISIONS 2026-09-10 as amended 2026-09-27): the controller stops acking lines but answers `?`, and `0x18` is the recovery. A stop there may be unconfirmed if the banner read is lost (Parking Lot: the drain can discard a stop's banner).
- **The Stop key does not arrive.** An input method claims the chord (older IBus, Windows Chinese IMEs, a composing engine; Design C), the platform takes it, or a native select menu holds the keyboard. The other chord and the button may still work; D-2, D-3, D-7 and D-8 record what arrives. Otherwise only the machine's e-stop works.
- **Kerf may have left the laser commanded on** (revision 4). A console M3, a Fire whose M5 failed, a program stopped between its M3 and its M5, or a connection that printed no banner. Kerf tracks this as *maybe on* (Design D) and opens no blocking dialog and no reload until an acknowledged M5, a confirmed stop or a banner reconnect, and Disconnect sends the stop reset first. Even "off" is Kerf's commanded state: an acknowledged M5 or a reset banner is what the controller said, and DECISIONS 2026-09-05 records a reset that did not stop the beam. The check is still the operator's eyes and the machine's e-stop.
- **Kerf's window cannot take input.** After B4, no native dialog or `confirm` opens unless the machine was proven idle with nothing in flight and the laser commanded off, nothing is admitted while one is open, and the Welcome Guide cannot reload the window under the same conditions. What remains: the webview's main thread hung; a native select menu (D-8); a motion that starts on the controller by itself, which Kerf does not command. In those, STOP, the keys and the crash screen may be unreachable, and only the machine's e-stop works.
- **The display fails.** A fault in the outcome code shows the failsafe banner. If the page cannot render at all, the crash screen has its own STOP; if the webview is gone, only the e-stop works.
- **The app process exits.** Nothing is sent. Whether the port closing resets the controller is unknown for the vendor fork.

**D1. Which keyboard shortcuts should stop the machine?** (Restated in full for revision 3, and corrected in revision 4: what the keys promise is narrower, and they now work while you are composing text.)
- **What exists today:** no key stops the machine. The only stop in Kerf is the STOP button, and while any dialog is open the first click on it only closes the dialog.
- **Where it lands:** two shortcuts that work in any Kerf dialog and any Kerf text box, the crash screen included, whenever the keystroke reaches Kerf. They send the same reset as the STOP button and are listed in the ? sheet and in STOP's tooltip. Revision 3 adds two things you would notice. The keys now also work while you are part-way through typing an accented or Asian-language character, if the typing system passes the key on. And the release note says plainly that a typing system or the computer can take a key before Kerf sees it, and that the STOP button or the machine's emergency stop is the answer then.

The key must be impossible to press by accident while typing, must not be Escape on its own (which closes dialogs, so closing Preferences would end a job), and must not collide with anything Kerf already uses. On some Linux desktops the typing system takes Ctrl+. for its emoji picker before Kerf sees it, and so do two Chinese typing systems on Windows. Your own desktop does not do this today (checked 2026-10-04), but a single safety key should not depend on that. None of the defaults checked on 2026-10-04 binds it: GTK, WebKitGTK, IBus, GNOME on your desktop, macOS, Windows and its two Chinese typing systems. It is one hand on the left. Cost: none beyond B2. **D2. While Kerf may have left the laser switched on, should it refuse file dialogs and the welcome guide, and should Disconnect send the stop reset?** (New in revision 4. You have not ruled on this; it ships as recommended unless you say otherwise.)
