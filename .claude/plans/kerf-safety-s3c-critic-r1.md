### Blocking traces and evidence

**A. Raw console jogs remain invisible.** Design §2 (plan line 63) excludes `$J=` from `motionPending`; `connection.ts:279–289` sets `jogPending` only inside `sendJogLine`. The console's raw `send` route therefore sets neither flag. With the last Idle position still fresh, issue a raw `$J=…`, then click a jog before the next status update: the click can be clipped against the old position and admitted. The out-of-scope promise, “S3c only makes it block the jog buttons while it runs,” is directly contradicted by the design. Raw console motion may bypass clipping by policy; it must still participate in the in-flight accounting promised here.

**B. An observed alarm need never reach the proposed setter.** `send()` at `connection.ts:622–642` logs response ALARMs; `surfaceUnsolicited` at `:51–68` logs drained ALARMs; `consumeStatusOutcome` at `machineStatus.ts:131–144` logs event ALARMs. None of those paths calls `setMachineState("alarm")`. Starting already homed, receive `ALARM:9` during re-home, then unlock before a poll captures Alarm: the plan clears the motion flag but does not necessarily clear the old `machineHomed`. A later Idle can admit a jog. T7 starts unhomed, so “leaves it false” does not test this. Clear trust before re-home and on every observed alarm; an Alarm snapshot is not a guaranteed event-delivery mechanism.

**C. The acknowledgement fence is incomplete.** Suppose motion A remains outstanding and motion B settles without `ok`: B clears the single flag while A is still pending. Separately, a poll begun after submission but before acknowledgement can have an unchanged `jogTick`; the specified predicate does not test whether a send remains outstanding. Rust `serial_send_inner` acquires a blocking command mutex (`src-tauri/src/commands/serial.rs:485`), whereas status uses `try_lock`; this prevents polling during an acquired command lock, but does not prove submission, native lock acquisition, and frontend promise completion are atomic. A poll can run while a submitted command is awaiting native scheduling or lock acquisition. Require explicit pending acknowledgements, not an inferred ordering from mutex behavior. Test both schedules with deferred invokes. Old completions must also be unable to restore homing or alter counters after disconnect/reconnect.

**D. Trust establishment overclaims its evidence.** The plan explicitly recognizes `$HX`, then awards whole-machine trust for any `/^\$H/i` command returning `ok`. If an accepted command homes only X, nothing established Y. If the target firmware rejects it, that must be demonstrated rather than assuming an `ok` proves both axes. Likewise `(0,0)` can recur after a move out and back; it is not evidence the head has never moved. `attestOrigin()` also lacks `motionPending`, `jogPending`, and `jobRunning` checks, allowing acceptance against an old fresh Idle while execution is pending. `softReset()` (`connection.ts:843`) and successful `emergencyStop()` (`:884` onward) do not necessarily call the alarm setter. Define how resets, spontaneous banners, and session changes revoke trust, even when no Alarm snapshot is delivered. This is a required lifecycle contract, not a claim that every reset necessarily loses coordinates on every firmware.

**E. The tests omit the firmware-dependent risk.** The owner hardware card only covers button Home, one jog, and an unspecified “Trigger an alarm.” Add a safe, specific alarm stimulus with laser isolation and travel limits; do not invite deliberate collision. Cover a console move followed immediately by a button jog, repeated/failed Home, reset/unlock, and the no-homing workflow on appropriate hardware. `.claude/DECISIONS.md` explicitly treats stock-GRBL evidence as insufficient proof about the vendor fork. Mocked browser `ok`/Idle is UI evidence, not physical qualification. If suitable hardware is unavailable, record that path as unqualified and define the fallback and release restriction.

## Stress test 1 — Pre-mortem

Three months out, a supposedly bounded button jog drives the head into the frame, damaging the gantry or pinching an operator's hand. This is the type-specific worst case for the changed motion gate; isolated laser power does not remove the mechanical hazard.

1. An operator uses a raw console `$J=…` and immediately presses an arrow. Neither pending flag covers the first command, so the second move is calculated from an obsolete position. The warning sign was the explicit `$J=` exclusion and absence of a raw-jog regression.
2. A previously homed machine fails a new Home and is unlocked before polling sees Alarm. Trust survives because the terminal ALARM was only logged. The next Idle enables motion from a position Kerf no longer has evidence to trust. The warning sign was T7's exclusively unhomed starting fixture.
3. A no-homing operator confirms origin while a console move is queued, relying on the visible zero position and present-tense button. The move changes the physical position before later jog admission. The warning signs were missing pending/job guards and a safety warning shown only after acceptance.

## Stress test 2 — Load-bearing assumptions

- **Every observed alarm becomes `setMachineState("alarm")`: very low confidence, contradicted by local code.** If false, trust survives known position-loss events. Resolve before implementation by enumerating and testing all response/event/snapshot paths.
- **One boolean and tick equality imply all motion acknowledged before Idle: low confidence.** If false, overlapping sends or a pre-ack poll reopen the stale-position admission window. Resolve before implementation with explicit command/session ownership and schedule tests.
- **Every successful `$H…` establishes both X and Y, in Kerf's assumed envelope: unverified for the supported firmware.** If false, partial or differently framed homing falsely enables bounded jogs. Resolve the supported command/frame contract before implementation; retain a hardware qualification requirement.
- **Zero MPos proves a valid opportunity to attest the connection origin: low confidence; current-position equality cannot prove history.** If false, the confirmation becomes an unsafe override. Resolve before implementation through an explicit attestation lifecycle and physical-origin instructions; the operator's truthful placement remains a disclosed human assumption.

## Stress test 3 — Inversion

Alternative (c), refusing jogging on `$22=0`, wins if a correct physical origin cannot be established and explained with the available evidence, or if no suitable hardware can qualify the proposed workaround. Those conditions are already partly present: zero MPos proves no physical corner, no-homing hardware testing is absent, and the plan admits this workflow is an interpretation for a machine the owner does not own. It is a defensible temporary fallback until that contract is established. Alternative (b), retaining untrusted jogging with a warning, would win only if the product explicitly abandoned the promised trusted-position interlock for that class; it does not satisfy the stated goal. A small shared motion lifecycle also beats the proposed minimal boolean if sends can overlap or complete across lifecycle boundaries; the asynchronous entry points already make that a condition the plan must handle.

## Overall verdict

**FAIL — gate blocked.** The plan addresses the right defects, but the proposed controls do not enforce its Summary: console jogs escape bookkeeping, logged alarms escape trust invalidation, broad homing recognition overstates what was homed, and the acknowledgement fence cannot represent concurrent outstanding commands. The existing test battery would let those defects pass because it largely exercises the proposed implementation's happy ordering. Correct the lifecycle and trust contract before implementation, then extend adversarial tests and hardware qualification to prove that contract; prose assurances and additional successful-Home fixtures will not close these gaps.
