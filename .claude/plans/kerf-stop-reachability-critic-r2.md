### Findings and required changes

**F1 — The busy guard admits exactly the state it promises to exclude.** Line 263 says “If `jobRunning || motionPending`” and “`motionPending` covers the jog window.” The latter is only the send window. `serial_session.rs:594–605` documents and implements a `MotionGuard` whose drop decrements the counter when a motion send returns. `machineStatus.ts:99` maps a reported jog to stored `run`, and :251 copies the native pending flag. Thus an accepted snapshot can report `run` with `motionPending: false` while the jog continues; `jobRunning` is false for a jog. B4 allows Open and Welcome Guide in that state. STOP also sets `jobRunning(false)` before the physical result (plan 157), so clearing the job flag is not evidence of safety. Extend the predicate to reported motion, hold/door, stale/unknown state and pending/uncertain stop outcomes as appropriate, using a conservative, documented admission rule. Test a real send completing followed by a running snapshot with pending false, and STOP followed immediately by Welcome Guide. Do not merely test booleans against the same boolean expression.

There is a second direction: “a native dialog the operator opened while idle, if a job could then start under it” (412) is still parked, and D-5 explicitly “does not fail the relay” (397). An already-awaiting `serial_job_begin` can resolve after a dialog opens; inability to click START under a dialog would not eliminate that schedule. Define mutual exclusion between blocking UI and admitted/in-flight hazardous actions, or prove the relevant platform and entry-point invariants before deferring it. An entrance guard alone cannot enforce this lifetime property.

**F2 — Episode identity is not current-operation identity.** “`stopJobBegan()` … clears a settled view and never a pending one” (233) and its positive test (311) explicitly preserve the counterexample: stop A finishes natively, its IPC reply is delayed, a new job is admitted, then A's reply resolves. Native `serial_stop_inner` sets phase Idle before returning its confirmed result (`serial.rs:1539–1554`); `serial_job_begin_inner` admits a job in Idle (:1617–1631). With no active/stopping JS session, a new admission can therefore precede delivery of A's reply. The old reply remains on the same connection and above its sampled floor, so the planned UI says “Stopped” during the new job. The copy's justification that “the job ended (`jobRunning` false)” (280) is false in that schedule. Preserve any necessary uncertainty warning, but revoke eligibility to display current confirmed status when a subsequent job/motion is admitted; test the delayed native-completion/new-admission ordering end to end.

Nor is the native-owner replay residual safe confirmation. Line 230 concedes a native-internal stop after the last snapshot can leave an unseen confirmed result that a later joiner replays, and excuses it as “a reset native really completed on this connection.” That does not confirm the stop now requested. A later native owner can be stalled while the joiner returns the old result above the floor; the owner is absent from the TS episode. “Minimum” therefore cannot protect this case. New episodes after an uncertain or overdue episode also need schedules where an earlier native owner is still outstanding. Either obtain trustworthy native operation identity in a separately scoped prerequisite or conservatively avoid confirmed wording where identity cannot be established. Explicitly listing the residual does not satisfy the claimed current-stop confirmation contract.

**F3 — Both supposedly independent keys share the same disabling condition.** Line 165 makes `isStopChord` “false whenever `e.isComposing`”; line 325 requires no stop for *both* chords during composition, and SR-36 enforces it. This is a planned loss of keyboard STOP during actual typing, not just an OS interception outside Kerf's control. The second key does not remove this shared failure. Establish a safe escape chord during composition and test delivered events and real IME composition in the target webview. If no such chord can be qualified, disclose the limitation and specify a validated accessible alternative instead of “from anywhere.” Do not casually remove the guard without verifying IME behavior.

**F4 — Catching errors is not a fail-safe outcome display.** Line 216 promises “a fault leaves the view exactly as it was,” then only discusses a view already pending. If the old view is confirmed and `beginStopAttempt` fails, the new reset was dispatched but the UI keeps “Stopped”; returning 0 supplies neither a new pending view nor necessarily a watchdog. The existing throw-in-setter test (302) does not assert safe operator-visible output. A catch also cannot roll back state already mutated before a throwing setter/subscriber. Specify mutation ordering, cleanup, and a visible uncertain fallback independent of the failing outcome path. Test failure from a previously confirmed state, partial setter/subscriber failure, and a fault inside the timer callback. If store failure prevents rendering, route to an independently viable crash/failure surface rather than claiming developer-console logging preserves guidance. Bound attempt retention while doing this.

**F5 — The baseline cannot satisfy its stated oracle.** B3 depends on B1 and B2 (348, 371), but line 389 calls its base “A7 merged, no TB1” and declares “A base run that stops is a broken script.” At the actual B3 parent, B2's keys must already stop. With no overlay, even the original STOP button stops. Name an immutable pre-TB1 comparison revision, separate it from B3's merge base, restrict pointer-negative controls to blocking surfaces, and state which regressions are measured at which revision. Add F1–F4 transition cases to the mutation/browser evidence; hundreds of modal-state combinations do not substitute for these asynchronous schedules.

**F6 — Seven seconds is a policy threshold, not a proven native upper bound.** Line 234 sums writes, submit delay and the nominal banner deadline into “about 6.05 s.” The inspected native path calls `port.flush()` after reset writes (`serial.rs:1463`, :1470), and its banner loop performs a blocking `read_until` before checking the deadline again (:1517). The plan itself acknowledges a hung drain/USB path (408). The stated sum does not bound those operations. Keep a conservative escalation timer, but describe it as an independent UI deadline, not exceeding native's worst case. Also correct the absolute “keys are unaffected” claim for a native select (414): the plan calls that platform behavior unverified and its owner checks do not exercise an open native select. Qualify and test it before using it as a safety backstop.

**F7 — Ownership and enforcement claims need mechanical consistency.** Line 381 allows “only the batch's files,” while 432–435 mandate ARCHITECTURE, ROADMAP and DECISIONS work not counted in batches already at eight files. Declare a separate serialized documentation commit or an explicit expanded waiver and scope allow-list. Put the promised deferral entries in ROADMAP before passing the indexing requirement; currently the specific new entries are only in the plan. B4 cannot be execution-parallel with B1/B2 while depending on B3, which depends on both; distinguish file independence from runnable parallelism. The B4 scan matches particular `dialogModule`/`dialog` spellings, so a new aliased or dynamic import evades “every door”; constrain imports and route all blocking calls through the guarded seam, with a mutation proving alias bypass fails.

**F8 — Record acceptance status without converting an unperformed check into closure.** Lines 392–402 name useful desktop/hardware checks, but 434 marks TB1 shipped with those checks in `next`. That is acceptable as implementation tracking only if explicitly distinguished from safety qualification. Require evidence for the webview-specific stop paths and corrected busy-guard schedules before declaring the corresponding reachability findings closed. Chrome evidence cannot settle native-dialog input ownership or IME delivery.

## Three stress tests

### Pre-mortem

Three months after release, a long jog receives its acknowledgment; the next status still says Run but pending is false. The operator opens Welcome Guide, the guard permits reload, and the page holding STOP disappears. The type-specific worst case is continued laser emission or head motion causing a burn, fire, injury, or damaged stock while the operator has lost the software stop. We should have noticed that the counter tracks a send, not physical completion (F1).

A stop resets successfully, but IPC delivery is delayed. A new job starts before the old result reaches the UI. “Stopped” then appears above that active job; alternatively, a native joiner replays an earlier reset while the current native owner is stuck. The operator delays using the physical e-stop because the display appears authoritative. We should have tested operation transitions and unseen native owners, not just two promises in one TS episode (F2).

An operator composing text presses both advertised Stop chords. Both return before dispatch. Meanwhile a presentation exception can preserve an earlier “Stopped” line and leave no new watchdog. The test suite passes because it explicitly requires no composing stop and only requires the helper not to throw. The missing signal was a safety oracle based on what the operator can do and see under failure (F3–F4).

### Load-bearing assumptions

- **Pending flags cover hazardous activity — low confidence, locally contradicted.** Native motion-send counter lifetime and TS status mapping show the guard can open during reported Run. Consequence: native UI/reload removes STOP during motion. Resolve before implementation (F1).
- **Same connection plus epoch floor means current stop — low confidence.** The plan itself admits unseen native results and preserves pending views across job admission. Consequence: a historical reset is promoted into present confirmation. Resolve before implementation (F2).
- **At least one keyboard stop remains available while typing — low confidence as specified.** Both matchers share the composing veto; OS delivery remains a separate qualification question. Consequence: no keyboard dispatch in a common input state. Resolve before implementation (F3).
- **The raised control escapes all current ancestor contexts in the shipped webview — moderate confidence, still unverified.** Local stacking analysis and browser tripwires are plausible, but Chrome is not target-webview proof. Consequence: pointer STOP remains hidden despite passing style assertions. Retain the real hit tests and require desktop evidence before safety qualification (F8).

### Inversion

The deferred native result-identity fix wins when a TS episode cannot observe the native owner or distinguish a historical reset from the requested one. That condition is already admitted at line 230. Avoiding native edits is a scope preference, not evidence that TS can recover identity the reply does not carry; either make that fix a prerequisite or weaken confirmation semantics conservatively. The portal alternative wins if required ancestor styling prevents the in-place raise, but a body portal does not defeat the browser top layer either: line 135's suggestion that portal (ii) wins when a future surface must use the top layer conflicts with line 132. Such a future design needs a top-layer-aware stop surface and input/focus proof, not merely a higher body z-index.

## Overall verdict

FAIL — block the gate. Revision 2 improves visible guidance and documents important residuals, but its strongest claims fail on reachable state transitions: B4 confuses send completion with motion completion, confirmation can outlive the operation it describes, and both advertised keyboard routes intentionally disappear during composition. The totality contract can preserve stale success, and the baseline oracle cannot run as written. These are implementable counterexamples to load-bearing controls, not requests for more prose or general caution; resolve them in the plan and its test oracles before implementation proceeds.
