### 2. The 0.0125 mm guard: lost burns, accumulated drift, and the product call
- **Can it drop a legitimate burning move and leave a gap?** Only a tail shorter than one step, and only where the refused move is followed by a non-burning move so that no later `G1` picks the distance up: a perforation or tab cut-end within a step of the previous written point, a path's final point, a sub-step overcut or lead-out. Each such gap is under 0.0125 mm on both axes, an order of magnitude below the kerf (0.1-0.2 mm), and is not a gap in the material. Where the refused move is followed by another `G1`, nothing is lost at all (next point).
- **Accumulated drift.** `pen.last` is the last position **written**, not the last geometric point. So successive refusals are judged against one fixed reference, the distance accumulates, and the first target at least one step away is written. Drift is bounded below one step per axis and can never sum into a gap. The classifier's D class judges against `a_st.pos` for the same reason, and the plan says so. Correct.
- **Is the guard ever stricter than the controller?** Yes, in one direction: a written delta under one step can still produce a step depending on where the absolute coordinates sit relative to step boundaries (e.g. X10.006 to X10.018 is 800.48 to 801.44 steps, one step). So the guard refuses some moves the controller would have executed. The cost is the chord error already named (Risk 2, "Decisions needed"); P2 is the check. Acceptable and correctly disclosed. The reverse never happens: a written delta of at least one step always moves at least one step.
- **Per-axis versus Euclidean.** Per-axis is right, because GRBL rounds each axis independently; a Euclidean threshold would pass a (0.009, 0.009) move that plans empty on both axes.
- **Text quantisation.** `q` re-parses `{:.3}` output, so the comparison sees exactly the digits the controller sees. 0.0125 has no 3-decimal representative, so the effective written threshold is 0.013 and there is no equality edge. `boundary_rounding` (raw 0.0127, written 0.012) and KL-M15 pin this. Correct.
- **Presentation under "Decisions needed".** Correct for the structured-decisions rule: it is engineering plumbing under Lee's 2026-09-25 delegation, so no prompt; the choice (one step, not "zero") is recorded with the narrower alternative, its risk (the kerf-offset pill junction stops the head at cut power under M3), the cost (sub-0.0125 mm chord error on finer machines), and reversibility (one constant, golden-neutral). It should add one clause: the constant is the **owner's** step size (Deferral 6), so the reversal path on another machine is "read `$100/$101`", not "change the number". Fold into Risk 2's existing text; no separate must-fix.

### 3. `M5` at the end of a mask fill

### 5. Deferral 2: "overcut plus lead-out burns a diagonal into the part on a hole". This batch or parked?
**Parked, and correctly so, but the deferral is mis-described and under-scoped, and that has to be fixed before Stage 3.5 writes it into the Parking Lot.** I traced the geometry. After an overcut the head is at `O = gpts[0] + ext·d_first` on the boundary (`:846-847`); the lead-out target is `L = gpts[n-1] + lead_out·d_last` (`:859-860`), the straight extension of the last edge beyond the start vertex. On any convex closed path, `L` is outside the polygon. So the `G1` from `O` to `L` is a chord that leaves the boundary: waste on an outer perimeter, **part** on a hole. The plan is right about that. What it misses: **`L` is outside the polygon with or without the overcut.** A lead-out on a hole always burns `lead_out` mm of the part beyond the start vertex, because Kerf's lead-out is a straight extension and knows nothing about which side is waste. And the lead-in uses the **outward** normal (`:547-579`), which on a hole is also into the part. The overcut only changes the scar from a straight stub to a diagonal chord. This is therefore not a new defect class; it is the same "which side is waste" blindness that Lee's 2026-09-10 ruling deferred into the geometry program ("Kerf compensation expands holes without accounting for which side is waste"). Ruling:
- **Not this batch.** It is a different class from "a burn that depends on state it did not set up itself" (the plan's class), fixing it is a product decision about where a hole's lead-in and lead-out should go, it changes output for every program with those features (`line_perf_overcut_leadout`, golden 12), and it needs its own owner check. Folding it in would break the classifier's "everything else byte-identical" discipline that makes this batch reviewable.
- **But it is a material-damage item, and it must be indexed as one.** Must-fix 5: rewrite Deferral 2 as "lead-in and lead-out do not know which side is waste: on a hole, both mark the part (lead-in by the outward normal, lead-out by straight extension); with an overcut the lead-out scar becomes a diagonal chord from the overcut end", route it to the geometry program under the 2026-09-10 ruling with the physical outcome in the Parking Lot line, and give Lee the same kind of plain-words workaround he was given for W2 ("no lead-in on rounded shapes"): lead-in and lead-out on outer cuts only until the geometry program lands. Razor's engine-arm review found W2 by asking the X1 question; this one was found the same way and deserves the same visibility, not a line about a "diagonal".

### Inversion: what would make a rejected alternative win?
- **Refuse only text-identical moves (the narrower guard).** Wins if the fork never plans empty blocks or never syncs on them, or if the machine's step size were far finer than 80 steps/mm. Neither is true or evidenced; `$100/$101 = 80` is read from the machine (`probe-20260914-153729.log:36-37`). The wider guard stands.
- **Seal in `mask_fill.rs` instead.** Wins if image output also needed sealing. It does not: image is its own fragment closed by the footer `M5`, and sealing there would break the scanner's own `M5`-count tests and the "no `M5` mid-row" invariant that `$32=1` G0-suppression relies on. Consumer-side seal stands.
- **Fix Deferral 2 in this batch.** Wins if it were the same class and needed no product call. It is not (Specific check 5). Park stands, with the rewrite.
- **Skip the matrix and trust the goldens.** Wins if the goldens reached the sites. They do not: 0 degenerate or sub-step `G1`s in all 16 (measured). The matrix stands, and KL-M4 to M13 depend on it.

## Overall verdict

**CONCERN, no gating FAIL.** The design is right and better than the instance fix Razor asked for: one start block that owns its own `G0` and mode line, one guarded writer for every burning vector `G1` that judges against the last written position with the controller's own rounding, one seal at the producer so a future regression fails dark. Every citation holds on the session branch, the golden predictions rest on measurements I reproduced, the reproduce-first and stop-on-mismatch discipline is as strong as engine-arm's and learns its lessons (Commit-1 before-set, per-corpus anti-vacuity, `--exact` regeneration, no second `KERF_UPDATE_GOLDEN` reader).
